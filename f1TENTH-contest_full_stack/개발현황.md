### 1. 출발 급가속 슬립 — 틀린 측정을 두 번 버리고서야 보였다

**틀린 측정 ① CTE.** 1랩과 이후 랩의 CTE 를 비교했더니 차이가 없었다.

```
주행     랩  CTE평균   p95    첫코너 CTE
213017    0   0.165  0.314      0.059
213017    1   0.157  0.330      0.051
213017    2   0.155  0.325      0.034
```

당연하다. **CTE 는 횡방향이고 문제는 종방향이다.** 위치가 앞서 나가도 CTE 는
깨끗하게 나온다. 08/05 aperture 문제에서 겪은 함정에 다시 빠질 뻔했다.

**틀린 측정 ② `amcl − odom` 을 차체좌표로 분해.** 부호가 앞선 측정과 반대로
나왔다. 두 프레임 사이에 **회전**이 있으면 원점에서 멀어질수록 차이가 커져서,
그 미분이 회전 성분에 오염된다. 크기도(100~200cm/s) 물리적으로 말이 안 됐다.

**되는 측정 — 프레임에 무관한 스칼라.** 0.6초 창에서

```
odom 이 말하는 이동거리  ÷  AMCL 이 말하는 이동거리
```

둘 다 경로길이라 프레임 오프셋·회전과 무관하다. 1보다 크면 바퀴가 헛돈 것.

bag 16개(08/10 주행 전체):

| 가속도 [㎧²] | 출발 0~5s | 5s 이후 | 차이 |
|---|---|---|---|
| 0.0~0.8 | 1.0332 | 1.0246 | +0.86% |
| 0.8~1.6 | 1.0344 | 1.0268 | +0.76% |
| 1.6 이상 | **1.0694** | 1.0360 | **+3.34%** |

**같은 가속도인데도 출발 5초 안쪽이 더 미끄러진다.** 단순히 "가속하면
미끄러진다" 가 아니라 **출발 자체가 특별**하다 — 정지마찰을 깨는 순간,
구동계 백래시, 하중이 뒤로 쏠리며 앞이 뜨는 것이 겹치는 구간이다.

누적하면 **출발 5초에 허위거리 87cm** (odom 17.35m vs AMCL 16.35m).
종방향은 복도에서 거의 관측되지 않으므로(08/10 측정: 앞뒤 0.2~1.0cm vs
좌우 6~7cm) AMCL 이 다 못 되돌리고 자세에 남는다 → 차가 "실제보다 더 갔다"고
믿어 **첫 코너를 일찍 돈다.** 출발선이 직선 한가운데라 매 주행 그랬다.

### 2. `LaunchLimiter` — 출발 3초만 가속을 따로 조인다

`launch_acc`(0.8㎧²) 로 시작해 `launch_time`(3s)에 걸쳐 `a_lon_acc`(1.6)로
**선형 복귀**한다. 감속에는 절대 걸지 않는다.

- **계단으로 풀지 않는 이유:** 그 순간 지령이 튄다(차가 프로파일보다 뒤처져
  있으니까). 그 계단이 곧 풀스로틀이라 막 벗어난 스핀 조건으로 도로 들어간다
- **창이 끝나도 `a_lon_acc` 로는 계속 건다.** 프로파일이 이미 **공간상**
  지키는 값이라 정상 주행에서는 안 걸린다. 걸리는 건 차가 뒤처졌을 때뿐이고
  그때는 걸리는 게 맞다

★ `speed_profile.LaunchLimiter` 로 **컨트롤러 공용**이다. bench(box) 수정을
두 차가 각자 디버깅한 전례가 있어서 map·stanley 가 같은 클래스를 쓴다.

**검증 — 같은 지표로 전/후:**

```
출발 5초 누적 허위거리    87.3cm  →  17.6cm     (−80%)
단위거리당               5.29cm/m →  1.11cm/m   (−79%)
같은 5초에 간 거리       17.35m  →  15.89m     (−8%)
```

거리는 8%만 줄었는데 허위거리는 80% 줄었다 — **"천천히 가서 덜 쌓인" 게
아니라 실제로 덜 미끄러진 것**이다. 이 구분을 위해 단위거리당으로도 쟀다.

**비용은 공짜가 아니다.** 프로파일 적분으로 잰 값:

| launch_acc | 1랩 | 손해 |
|---|---|---|
| 없음 | 15.64s | — |
| 0.6 | 16.94s | +1.30s |
| **0.8** | **16.80s** | **+1.16s** |
| 1.0 | 16.66s | +1.02s |
| 1.2 | 16.54s | +0.90s |

**누적되지 않는다** (3랩에서도 +1.20s) — 출발 한 번의 값이다.
창 길이는 거의 무의미했다(1.5s 든 3.0s 든 0.1s 차이). 프로파일 자신의
`a_lon_acc` 로 금방 복귀해서다. **실제 노브는 `launch_acc` 하나다.**

0.8 로 시작한 이유: 실측에서 1.6 이상만 명확히 나쁘고(1.069), 0.8~1.6 구간은
1.034 로 같아 그 아래를 더 파도 근거가 없다. μ 때처럼 **되면 올리는** 방식.

### 3. μ = 0.42 확정 — 한계를 위아래로 짚었다

| μ | η | 결과 |
|---|---|---|
| 0.40 | 0.6~0.7 | 여유 있음 (제동 예산의 45%만 사용) |
| **0.42** | **1.0** | **깨끗하게 완주** |
| 0.45 | 1.0 | 코너 슬립 — 벽에 닿을 뻔 |

08/09 의 "μ_eff ≥ 0.400 **하한** 확정" 에서 한 걸음 나아갔다. 이제 위에서도
막혔으니 **양쪽에서 좁혀진 값**이다. `μ_eff = 0.42 × 1.15 = 0.483`.

마지막 4주행:

| 주행 | 랩 | 랩타임 | v최대 | CTE평균 | p95 | 곡률비 | 직선 δσ |
|---|---|---|---|---|---|---|---|
| 000337 | 2.88 | 16.02 | 4.57 | 0.109 | 0.221 | 0.94 | 0.038 |
| 000618 | 2.90 | 14.65 | 4.81 | 0.121 | 0.280 | 0.87 | 0.045 |
| 000816 | 2.99 | **14.00** | **5.05** | 0.154 | 0.309 | **0.84** | 0.056 |
| 001033 | 2.98 | 14.39 | 4.92 | 0.120 | 0.267 | 0.91 | 0.047 |

**곡률비**(주행 곡률 ÷ 기준 곡률)가 판정 지표다. 1.0 이 목표이고
`>1` 은 안쪽으로 파고듦(과조향), `<1` 은 바깥으로 밀림(슬립).
가장 빠른 000816 의 0.84 가 다른 주행보다 낮다 — 보고된 "고 μ 에서 코너
슬립" 과 방향이 일치한다. 0.91(001033)이 지금 자리다.

> ⚠ 대회 노면(우레탄)은 다르다. **현장에서 같은 방법으로 다시 잴 것** —
> η 스윕이 곧 μ 측정이다.

### 4. `gains.yaml` 이 조용히 거짓말하고 있었다

주행별 mu 를 읽으려다 발견했다. 차량별 값 분리(`.car`, 08/10) 이후
**mu·grip_util·l1_k 처럼 실제로 주행을 결정한 값이 `race_script.yaml` 에
없다.** 그런데 주행 스냅샷은 그 파일만 복사하고 있었다.

```
gains.yaml 에 찍힌 값   mu 0.348
실제로 주행한 값        mu 0.42
```

08/10~11 로그를 사후 분석할 때 "이 주행의 mu 가 얼마였나" 를 읽을 수 없었다.
**틀린 값을 자신 있게 적어두는 스냅샷은 없느니만 못하다.**

→ `write_run_config()` 로 통일(세 컨트롤러 공용). 차량 오버레이를 구분선
아래에 덧붙여 **나중 키가 이기는 순서 = 실제 적용 순서**로 남긴다.
오버레이가 없으면 그 사실을 파일 안에 경고로 적는다 — 조용히 빠지는 게
제일 나쁘다.

## 08/10 밤 (젯슨) — AMCL 이 계속 차를 뒤로 당기고 있었다

고속(η 0.9~1.0)에서 코너를 일찍 돌고 한 번은 위치가 통째로 튀었다.
"경로 추종보다 AMCL 정확도가 더 문제 아니냐" 는 지적에서 출발했다.

### 종방향 보정이 전부 한쪽으로 쏠려 있었다

AMCL 보정을 차체좌표로 분해하고 가속도별로 나눴다(음수 = 뒤로 당김):

| 가속 구간 | 종방향 [cm/s] | 횡방향 |
|---|---|---|
| 감속 | −1.34 / −0.72 | −3.67 / +2.11 |
| 정속 | −7.44 / −0.86 | −2.18 / +3.06 |
| 약가속 | −8.42 / −6.40 | +5.79 / −1.30 |
| 급가속 | **−15.07 / −12.59** | −2.36 / +2.07 |

종방향은 **전부 음수이고 가속에 비례**한다. 횡방향은 부호도 크기도 일정치
않다 → 종방향에만 있는 **계통 오차**다. 잡음이 아니다.

08/08 슬립 분석의 "휠이 1.21배 빨리 돈다" 와 같은 현상인데, 그때는 μ 측정
오염 요인으로만 봤다. **위치추정에도 그대로 들어가고 있었다.**

> ※ 이 분해 방식 자체가 프레임 회전에 오염된다는 걸 08/11 에 알았다.
>   결론(휠 스핀)은 프레임 무관 지표로 다시 확인해 유지됐다.

### `alpha3` 0.10 → 0.03 → **0.12** (직전 판단 되돌림)

종방향에 두 요인이 맞선다:

- **(가)** 진행방향은 관측되지 않는다 → odom 을 믿어야 한다
- **(나)** 그런데 그 odom 이 가속 중에 계통적으로 틀린다

**(나)가 이긴다.** odom 이 계통적으로 틀리는데 `alpha3` 를 조이면 **틀린 값을
더 믿게** 만든다. 앞선 커밋은 (가)만 보고 내린 결정이었다 — 관측 기하만 보고
센서 편향을 안 봤다. **한쪽 측정만으로 결론 내면 안 된다.**

### `a_lon_acc` 0(자동) → 1.6㎧²

```
자동 유도   μ_eff·g·lf/L = 2.48㎧²
실측 급가속              1.61㎧²
```

**프로파일이 낼 수 없는 가속을 1.5배로 요구하고 있었고, 그 차이가 휠 스핀으로
나갔다.** 못 낼 가속을 지시하면 바퀴만 헛돈다.
랩타임 손해는 거의 없다 (η0.6: 15.7 → 15.6s) — 코너가 촘촘해 긴 가속 구간이
없어서다.

### odom 선형보간 — 시간 양자화 오차

AMCL 보정을 계산할 때 **가장 가까운 odom 샘플**을 쓰고 있었다. 50Hz 라
최대 20ms 어긋나고, 5㎧ 에서 그대로 **10cm** 의 가짜 보정이 된다.
이진탐색 + 선형보간(yaw 는 wrap 처리, 외삽 없음)으로 바꿨다.

→ 보정 점프 **60~65% 감소**, 직선 CTE 진동 **93.4cm → 8.1cm**.

### 트랙 자체가 종방향으로 모호하다

맵에서 자세를 앞뒤/좌우로 흔들며 스캔 정합 잔차를 재니:

```
앞뒤로 흔들 때   0.2~1.0cm 변화   ← 거의 안 변한다 = 관측 안 됨
좌우로 흔들 때   6~7cm 변화
s=12m, s=16m     둘 다 0.09cm     ← 2.44m 점프가 일어난 지점
```

복도에서 앞뒤 위치는 **원리적으로 관측되지 않는다**(aperture 문제).
빔 수를 늘려도 안 풀린다 — 정보가 없는 것이지 해상도가 모자란 게 아니다.

### 코드는 합치고 값만 분리한다 (`.car`)

브랜치로 차를 나누면 **코드까지 갈라져 같은 버그를 두 번** 고치게 된다.

```
config/vehicle_car1.yaml    1호차 실측값,      git
config/vehicle_car2.yaml    2호차,             git

        ↓ config/apply_vehicle.py  (race.sh 가 매 실행 호출)

config/.vehicle_overlay.yaml    race_script.yaml 위에 덮을 값  .gitignore
```

### `--rmin` 이 안 먹던 진짜 이유 (세 겹)

1. 내가 쓴 수렴식이 제약을 **느슨하게** 하는 방향이었다
   (`r_eff *= r_act/rmin` → `rmin/r_act`)
2. **최적화한 곡선과 출력 곡선이 달랐다** — QP 는 `calc_splines` 로 풀고
   출력은 `splprep` 로 다시 매끈하게 만들고 있었다
3. 이동량이 격자보다 커서 선형화가 무효했다

→ 재선형화 반복(iqp) + 신뢰영역 + `eval_spline_dense`(최적화 대상 = 출력).

### 중심선이 벽에 붙어 있었다

라인이 코너 모서리에 너무 가까웠다. 중심선 재중심화(12회)를 넣었는데
**부호를 처음에 반대로 넣어 비대칭이 70% → 97% 로 악화**했다.
양쪽을 다 실측해 `+n` 이 맞음을 확인(70% → 10%).

부수로 `wallclear` 검사가 `safety_m` 을 이중으로 세고 있어 **중심선조차
탈락**시키던 것, 오류 메시지가 `--safety` 를 **줄이라**고 거꾸로 안내하던 것도
고쳤다.

### 1. 고속 직선 요 진동 — 잡음이 아니라 한계 사이클이었다

직선 구간(κ<0.15)만 뽑아 주파수 분해:

```
3.1㎧ : δ 3.66° / 헤딩 3.88° / CTE  3.9cm  @ 0.68Hz
4.0㎧ : δ 6.42° / 헤딩 7.70° / CTE 12.2cm  @ 0.51Hz
```

셋이 **같은 주파수로 함께** 흔들리고 속도 30% 상승에 진폭이 2~3배가 됐다.
센서 잡음이면 이렇게 안 된다. 헤딩오차→조향 상호상관으로 루프 지연을 재니
**290ms**(|r|=0.98) 였다.

**원인 ① `steer_alpha` 가 루프 주기에 걸려 있었다.**

```
시정수 = -Δt/ln(alpha)
  실차 map_controller : create_timer(0.02)     → 50Hz  → 170ms
  시뮬 map_controller : /ego_racecar/odom 콜백 → 250Hz →  34ms
```

같은 0.8892 가 실차에서 **5배 무겁다.** 옵티마이저는 34ms 짜리 필터로
최적화해놓고 실차엔 170ms 가 걸렸다. 측정된 290ms 중 170ms 가 이것이다.
오늘 반복된 형태와 같다 — 값의 의미가 쓰는 곳마다 다른데 숫자만 옮긴 것.

**원인 ② 슬립보정 α_f 가 L1 의 속도무관 설계를 깬다.**

`a_lat = 2v²sinη/L1` 에 `L1 = l1_k·v` 를 넣으면 `a_lat ∝ v` 다.
헤딩오차 1rad 당 (모델, 실측 δ/헤딩과 15% 이내 일치):

| v | δ_kin | α_f | α_f/δ_kin |
|---|---|---|---|
| 2.0㎧ | 0.440 | 0.275 | 0.6배 |
| 4.0㎧ | 0.283 | 0.707 | 2.5배 |
| 6.0㎧ | 0.188 | 1.060 | **5.6배** |

L1 법칙 자체는 잘 돌고 있다 — δ_kin 이 오히려 줄어든다(속도무관 설계).
깨는 건 α_f 다.

→ `steer_alpha` 0.8892→0.555, `l1_k` 0.5837→0.75.
   **직선 CTE ±0.126 → ±0.097m, δ 표준편차 0.128 → 0.050.** 해결.

### 2. 그러자 코너에서 안쪽으로 파고들었다

CTE 부호 해석에 기대지 않으려고 주행 궤적을 0.1m 로 재샘플해 **곡률을 직접
비교**했다:

```
s=20m  κ 0.53 → 실제 1.01   1.89배
s=24m  κ 0.77 → 실제 0.96   1.24배
s=28m  κ 0.68 → 실제 0.82   1.20배
```

정상선회 기준 α_f 를 계산하면 기구학항만큼 크고 좌 한계(20.73°)를 넘는다:

```
κ0.77 v1.99㎧ : δ_kin 14.26° + α_f 11.47° = 25.73°
κ0.53 v2.81㎧ : δ_kin  9.92° + α_f 16.63° = 26.55°
```

그런데 실차는 모델보다 **덜** 미끄러진다(곡률비 1.2~1.9 가 그 증거 — 진짜
슬립 중이면 덜 돌아야 한다). `mu`(0.348)나 `pac_b`(3.8)가 낮게 잡혀 있다는
뜻인데 둘 다 [미검증]이다.

→ `map.slip_gain` 신설(0.5). **곡률비 1.00~1.07** 로 정상화.
   mu 를 올려도 α_f 는 줄지만 속도 프로파일까지 바뀐다 — 조향만 떼어냈다.

### 5. 출발 정렬 — 수동 자세를 덮어쓰고 있었다

`auto_localize` 는 기동 2초 뒤 `/initialpose` 를 쏜다. `_try()` 는 "정지
상태인가"만 봤지 **"이미 사람이 정해줬는가"는 안 봤다.** RViz 2D Pose
Estimate 로 손수 찍어둬도 2초 뒤 덮어써서 **반드시 점프**가 났다.

→ `/initialpose` 를 구독해 외부 발행이면 양보(우리 발행은 0.5s 무시로 구분).

**"될 때도 있고 안 될 때도" 의 정체도 잡았다.** 출발 지점 스캔으로 정렬 비용을
직접 흔들어 봤다:

| 이동 | 진행방향 오차증가 | 옆방향 |
|---|---|---|
| 5cm | **+0.00cm** | +0.45cm |
| 20cm | **+0.73cm** | +5.47cm |
| 40cm | +2.28cm | +13.27cm |

**진행방향으로 20cm 를 움직여도 비용이 0.73cm 밖에 안 는다** — 옆방향의 7.5배
차이다. 직선 복도라 그 방향 위치가 기하학적으로 관측되지 않는다(aperture
problem). 격자 탐색은 사실상 아무 데나 고르고 실행할 때마다 답이 달라진다.

평균오차(fit)만 보면 안 보인다 — 어느 지점을 골라도 fit 이 비슷하니 "잘
맞았다"고 보고한다. 그래서 ±20cm 흔들어 두 방향 비용 증가를 로그로 찍고,
진행방향이 2cm 미만이면 경고하게 했다.

**알고리즘으로 못 고친다. 출발 위치를 코너가 보이는 쪽으로 옮기는 게 답이다.**

### 레이싱라인 — 최적화한 곡선과 주행하는 곡선이 달랐다

   스무더가 정하고 있었다

→ 재선형화 반복(TUMFTM iqp) + `eval_spline_dense`(최적화 대상 = 출력 곡선) +

  부수로 `min_w 0.20` 이 없는 폭을 만들어내던 것(실제 0.12m 병목)도 잡았다.

Pacejka)에서만 최적화한 파라미터가 실차로 그대로 넘어갔다 — sim-to-real 이 유효하다는
첫 증거다. 다만 세 가지 증상이 남았다: 직선→코너 전이에서 좌우 흔들림, 인코스로 들어가
바깥으로 밀림, 180° 헤어핀에서 뒤가 미끄러지는 느낌.

이번 주행부터 로그에 열이 넷 늘었다 (`speed` **실측** / `steer` / `cmd_v` / `yaw` / `near`).
그 덕에 세 증상이 전부 판정됐고, 예상 못 한 것 하나가 더 나왔다.

### 1. q2 가 q1 속도로 달리고 있었다

`race.launch.py` 가 `grip_util` 을 `mode:=` 오버라이드 **적용 전에** 풀고 있었다.

```python
mode = cfg['mode']              # ← yaml 의 mode (q1)
grip_util = _gu.get(mode, ...)  # ← 여기서 이미 0.8 로 결정
for a in sys.argv:              # ← 오버라이드는 그 다음
    if a.startswith('mode:='): mode = a.split(':=')[1]
```

`./race.sh q2` 를 하면 **컨트롤러만 q2 로 바뀌고 속도는 q1 이 정한 η=0.8** 을 썼다.

로그가 그대로 말해준다:

```
q2 3회의 cmd_v 중앙 :  3.02  3.02  3.02
q1     의 cmd_v 중앙 :  3.03
```

4.9㎧ 로 장애물에 돌진했으니 회피가 될 리가 없다. 블록을 오버라이드 뒤로 옮겼다.

의도했던 `q2: 0.1` 은 이제 **진짜로 반영된다** — 그 값이면 중앙 1.1㎧ 로 기어간다.
0.5(중앙 2.43, 최고 4.00)로 조정했다. 회피 여유는 속도를 죽여서가 아니라
호라이즌으로 버는 게 맞다.

읽는 곳과 쓰는 곳이 갈리는 함정(`docs/grip_util_shadowing.md`)의 사촌 격이다.
이번엔 키가 아니라 **순서**였다.

### 2. 회피 호라이즌이 필요량의 60%

`obs_horizon_min: 1.8` 은 주석에 `= 2 × l1_min(0.90)` 이라고 적혀 있다.
그런데 지금 `l1_min` 은 **1.4431** 이다. 값을 올릴 때 호라이즌을 같이 안 올렸다.

4㎧ 에서 실제로 필요한 거리:

```
L1 = max(1.4431, 0.5691 × 4.0) = 2.28 m
오프셋 수렴거리  1.8 · L1/√2   = 2.90 m
기준선 램프      0.6m ÷ 0.9㎧  = 0.67s = 2.7 m
                                  ─────────
                          합계 ≈ 5.6 m

실제 호라이즌 = 3.0 m   ← obs_horizon_max 에 걸림
```

**감지한 순간 이미 늦는다.** `min/sec/max` 를 2.9/0.7/5.0 으로,
`shift_rate` 를 0.9 → 2.0 으로 올렸다. 통로는 직선이 아니라 레이싱라인을 따라
뻗으므로(`_predicted_track_path`) 호라이즌을 늘려도 코너 벽을 긁지 않는다.

`frenet.enabled` 가 한 블록 안에 **두 번** 있는 것도 발견해 지웠다.
YAML 중복 키는 뒤엣것이 조용히 이긴다 — 지금은 둘 다 true 라 무해했지만
하나만 고치면 안 먹는 전형적 함정이다.

### 3. 구동계 지연 250~290ms — 처음 실측했다

`speed`(실측)와 `cmd_v`(지령)의 상호상관 최대 지점:

```
q1 17:08 :  6샘플 246ms  (r=0.979)
q2 17:10 :  7샘플 291ms  (r=0.950)
q2 17:13 :  7샘플 287ms  (r=0.957)
q2 17:14 :  6샘플 252ms  (r=0.970)
```

헤어핀 진입에서 이렇게 나타난다:

| s | 프로파일 | 지령 | **실측** | CTE |
|---|---|---|---|---|
| 12 m | 2.98 | 3.78 | **4.42** | +0.126 |
| 14 m | 1.80 | 2.09 | **3.30** | +0.061 |
| 16 m (κ=1.28) | 1.57 | 1.77 | 1.83 | **−0.390** ← 바깥으로 밀림 |

**그립이 모자란 게 아니라 감속을 늦게 시작한 것이다.** 4.7㎧ 에서 250ms 는 1.2m 다.

`limits.speed_lag: 0.25` 를 신설했다. 앞으로 `v·t` 만큼의 구간에서 프로파일의
**최솟값**을 취해 지령한다. 보정은 **감속 방향에만** 건다 — 가속까지 앞당기면
코너를 다 빠져나오기 전에 밟게 되어 마찰원을 넘는다. 브레이크는 미리, 액셀은 제때.

검증: 제동구간(s=12~14)에서 0.85~0.90㎧ 조기 감속, **속도가 올라가는 점 0개**.

이건 **시뮬에 없는 동역학**이다. `sim_vehicle.steer_delay: 14`(140ms)는 조향 지연이고
속도 지연은 모델에 아예 없다. 노트북이 넣고 재최적화해야 한다.

### 4. ★ 차가 왼쪽으로 안 꺾이고 있었다

가장 예상 못 한 것. 조향 포화 112회가 **전부 좌회전**이었다.
우조향은 최대 −0.333 으로 한계(−34.2°) 근처에도 안 갔다 — 이 트랙은 전 구간 좌회전이다.

원인은 08/07 에 `steer_trim.py` 가 자동으로 옮긴 중립값이었다.

```
중립  0.425 → 0.4249 → 0.4041 → 0.3954   (네 번의 자동측정)

servo = 0.3954 − 0.761·δ,   servo_min = 0.15
  → 좌 한계 δ = (0.15 − 0.3954)/(−0.761) = 0.3225 rad = 18.48°
     그런데 max_steer 는 0.36 rad = 20.63°
```

**그 사이 2.15° 의 명령은 `vesc_driver` 가 조용히 잘라버린다.**
이번 q1 지령의 **25.8%** 가 이 유령 구간이었다. 컨트롤러는 20.6° 를 줬다고 믿고
다음 스텝을 계산하는데 바퀴는 18.5° 에 멈춰 있었다.

더 중요한 건 기하다:

```
라인 최소반경 (5점 평활)   0.91 m   → 필요 조향 19.5°
차량 최소회전반경          0.97 m   → 좌 한계 18.48°
```

**속도와 무관하게 헤어핀 라인을 못 돈다.** s=16m 의 −0.39m 밀림이 그립이 아니라 이것이었다.

08/05 에 락을 푼 사본으로 기구 스토퍼를 실측해뒀다(좌 servo **0.100**).
0.02 여유를 남겨 `servo_min` 을 **0.12** 로 넓혔다:

| | 좌 한계 | R_min | 라인 0.91m |
|---|---|---|---|
| 수정 전 | 18.48° | 0.970 m | ✗ |
| 수정 후 | **20.73°** | **0.856 m** | ✓ |

없던 성능을 만든 게 아니라 **`max_steer: 0.36` 이 이미 주장하던 값을 실제로 낼 수 있게**
한 것이다. 캘리브레이션(`gain`/`offset`)은 안 건드렸다 — `servo_min` 은 기구 스토퍼를
안 밀려고 두는 소프트 리밋이다.

⚠ 08/05 에 0.11 로 넣었다가 되돌린 적이 있다(`a053912`). 그때 사유는 서보 손상이 아니라
**Stanley gain 1.6 이 조향 포화를 유일한 감쇠원으로 쓰고 있어서** 한계를 넓히자 직선에서
발산한 것이었다. 지금은 MAP + `steer_alpha 0.8869` 라 조건이 다르다. Stanley 로
되돌아갈 때 반드시 재검토할 것.

⚠ 스토퍼 실측이 틀렸으면 서보가 기구 스토퍼를 밀어 스톨 전류로 탄다.
**첫 주행 전 `./race.sh box` 로 좌우 끝까지 흔들어 소음·발열 확인.**

## 08/07~09 (젯슨) — 계측 신뢰성 확보 · μ 실측 · 속도 프로파일 물리화

μ 를 재려고 slip_friction 을 돌렸는데 값이 안 맞아서 파고들었더니, 계측
파이프라인 전체에 부호·기하·관측성 문제가 겹쳐 있었다. 그걸 걷어내는 과정에서
**오도메트리가 8.9% 틀렸다**는 것과 **μ 가 1.05 가 아니라 0.40** 이라는 게 나왔고,
그러면 속도 계획 방식 자체가 틀렸다는 결론까지 이어졌다.

### 1. slip_friction 이 애초에 동작할 수 없는 상태였다

`_icp` 가 찾는 것은 `src→dst` 변환인데 이는 **차체 운동의 역**이다. 그걸 그대로
속도로 썼다. 전진 중 `v̂_x` 가 음수로 나오니 `|v_wheel − v̂_x|` 가 항상 ≈2v 가 되어
**슬립 판정과 자동 임계값 교정이 통째로 무의미**했다. 합성 점군으로 확인:
차 +0.20m 전진 → 옛 코드 반환 −0.20.

같이 나온 것들:

* **조향 클램프 누락** — `/commands/servo/position` 은 클립 **전** 지령이다. 좌회전
  기구 락 20.7° 를 지령값 31.5° 로 기록해 `ω_kin` 이 1.5배 부풀었고, 그게
  각슬립이 79~91% 행에 찍힌 주원인이었다.
* **레버암 미보정** — ICP 는 LiDAR 위치의 속도를 재는데 슬립각은 차체 기준이다.
  ω 80°/s 면 0.27×1.4 = 0.38㎧ 가 횡속도로 새어든다. base_link→laser TF(0.27m)
  로 보정하니 |β| 중앙값이 **13.2° → 2.4°**.
* **ICP 베이스라인** — `icp_hz` 가 실행 빈도만 낮추고 정합 베이스라인은 항상
  스캔 간격(25ms)이었다. v_y 0.2㎧면 횡변위 5mm 로 LiDAR 노이즈에 묻힌다.

### 2. 종방향 속도는 스캔 정합으로 **얻을 수 없다** (원리적 한계)

`icp_hz` 를 낮춰 베이스라인을 100ms 로 늘렸더니 `vx_lidar` 가 0 에 락인됐다.
초기값 0 → ICP 가 0 반환 → 영원히 0. 다중 시작(잔차 선택)을 넣어도 안 풀려서
**잔차 지형**을 직접 재봤다:

```
dx 를 0 → 0.36m 로 훑어도 잔차가 20.2 ~ 21.2mm 로 평평   ← 정보가 없다
dy 를 ±0.1m 옮기면      잔차가 20.6 → 107mm 로 급증      ← 강하게 구속
```

진행 방향과 나란한 벽이 지배적이면 종방향으로 얼마를 움직이든 스캔이 똑같아
보인다(개구 문제). **튜닝으로 못 고친다.** 그래서 `enable_lin_slip` 을 기본 OFF 로
하고, 참고 논문(2509.15423)이 `v̂_x` 를 쓴 건 스캔 정합이 아니라 **지도 기반 EKF**
라서라는 것도 확인해 주석에 남겼다.

같은 기하가 횡방향은 반대로 강하게 구속하므로 `v̂_y`·`ω̂` 는 쓸 수 있다 — 슬립각
α 에 필요한 건 이쪽이다.

### 3. 오도메트리가 8.9% 틀렸다 (줄자 6회 실측)

정상 선회에서 `a_y` 가 `v·ω` 보다 28% 컸다. ω 는 IMU 자이로와 LiDAR ICP 두 독립
센서가 기울기 1.01~1.06 으로 일치하므로, 남는 건 `v_wheel` 이었다.

`odom_scale` 도구를 만들어(줄자 거리 vs /odom) **6회 측정 → 표시 속도가 실제의
91.1%**. `speed_to_erpm_gain: 4614 → 4203`. IMU·LiDAR 를 전혀 안 쓰는 독립 검증이다.

★ 같은 지령에 차가 약 9% **느려진다** — 그동안 계획보다 빨리 달리고 있었다.

### 4. 남은 12.6% 는 차체 롤 — 종축이 대조군이 됐다

속도(8.9%)와 가속도계 스케일(정지 시 중력 1.036g = +3.6%)을 다 보정해도 `a_y` 가
`v·ω` 보다 11% 컸다. 축 매핑을 독립 기준으로 교차검증했더니:

```
imu.y vs 종가속 dv/dt : 기울기 −0.993  R²=0.412
imu.x vs 횡가속 v·ω   : 기울기 +1.110  R²=0.896
```

같은 가속도계·같은 스케일인데 **횡축만** 11% 틀린다. 스케일 문제라면 두 축이 같이
틀려야 하고, 축이 꺾였다면 상관이 뒤바뀌어야 한다. **롤은 종축 둘레의 회전이라
횡축만 기울여 중력을 섞으므로** 관측된 패턴과 정확히 일치한다. 롤 기울기로 환산
6.3°/g 로 RC 카 정상범위다.

결론: **6축 IMU 는 횡가속과 중력의 기울기 성분을 원리적으로 구분할 수 없다**
(랭크 부족). 필터를 달아도 안 풀린다 — 애초에 노이즈가 아니라 편향이다
(R²=0.9, 절편 0). 그래서 μ 는 `a_y` 가 아니라 **`v·ω`** 로 잰다.

### 5. μ = 1.0489 → 0.400 (실효 그립)

연습장 노면이 화강석 타일 + 먼지다. 서로 독립된 세 방법이 0.30~0.48 에 모였다:

1. `μ_k = v·ω/g` 99%p 0.487 → 휠 스핀 보정 → **0.40**
2. 기하학 — 조향 20.7°(기구학 반경 0.85m)인데 실제 약 3.0m 로 밀림 → 0.30~0.36g
3. 팀원 곡률 실측 `A_LAT_MAX 3.7㎧²` → 오도메트리 보정 후 **0.45g**

★ **`mu` 는 마찰계수가 아니다.** MAP 논문 III-B 가 `"peak value D̃ is in fact
μ·Fz,i·Di"` 라고 명시한다 — 실효 최대 그립은 **`mu × pac_D`** 다. 논문 자체 수치로
검증: `1.0489 × 1.2084 = 1.267g` ↔ 본문 `"lateral accelerations of 1.25 g"`.
그래서 실측 0.40g 를 재현하려면 `mu = 0.40 / 1.15 = 0.348` 이다.

같이 찾은 것: **컨트롤러(B=3.8/D=1.15)와 LUT 생성기(B=3.629/D=1.2084)가 서로
다른 타이어 곡선**을 쓰고 있었다. `race_script.yaml [map]` 을 단일 소스로 통일.

### 6. 08/08 실차 μ 측정 — 데이터를 못 썼다

`./race.sh slip` friction 모드로 원 주행. 결과는 못 쓰는 데이터였다:

* 충격 **17.2g** 포함, 1.5g 초과가 전체의 **32%** (벽 충돌 여러 번)
* 휠 스핀 — `a_x = 0.825·(dv_wheel/dt)`, 휠이 차보다 1.21배 빨리 돈다 →
  `v_wheel` 이 부풀어 `μ_k` 도 과대평가
* 한계를 한참 넘겨서 돎 — 조향 20.7°(기구학 반경 0.85m)로 실제 3.0m, **3.5배**

도구에 충격 제외·오버스티어 제외·휠 스핀 진단·`--radius`(휠·롤 무관 `μ=R·ω²/g`)를
추가했다. **다음엔 정반경(constant-radius) 방식**으로 — 반경을 고정하면 자이로만
써서 스핀·롤 둘 다 피할 수 있다.

### 7. Frenet 회피를 독립 노드로 분리

MAP 컨트롤러에는 회피가 **아예 없었다.** `/scan` 구독조차 없어 장애물을 보지도
못했고, `controller: map` + `mode: q2` 여도 아무 경고 없이 회피 없이 달렸다.

회피 로직이 stanley 에만 있고 pure_pursuit 가 일부를 복사해 간 상태라, MAP 용
사본을 하나 더 만들면 셋을 동기화해야 한다. 그래서 **`obstacle_avoid.
ObstacleAvoidMixin` 으로 추출**(519줄 + 모듈함수 48줄):

* 손으로 옮기지 않고 줄 범위를 프로그램으로 잘라내 원문을 보존
* git HEAD 원본과 `inspect.getsource` 를 15개 전부 대조 — **코드는 한 글자도 다르지
  않다** (차이는 다음 섹션 헤더 주석 3줄뿐)
* `StanleyController(ObstacleAvoidMixin, Node)` 로 상속만 변경

`frenet_planner` 노드가 `/frenet/offset`(Float64) 을 발행하고 컨트롤러가 소비한다.
경로(Path)가 아니라 스칼라 d 를 넘기는 이유는 웨이포인트에 **속도 프로파일이
실려 있어서**다.

★ **컨트롤러별 호라이즌** — d 에 수렴하는 속도가 다르다. Stanley 는 전방주시
지연이 없어 즉시 반응하지만, MAP/L1 은 2차계(ζ=0.707)라 오버슈트는 4.3% 로 작아도
**상승거리가 1.8·L1/√2 ≈ 1.15m** 다. Stanley 기준 `obs_horizon_min`(0.8m)을 그대로
쓰면 다 피하기 전에 장애물에 닿는다. 경험칙 **호라이즌 ≥ 2 × L1**.

### 8. 속도를 "상한" 이 아니라 물리로 정하게 바꿨다

Stanley 가 저속에서 등속으로 도는 이유가 여기 있었다. `clip(v, min, max)` 인데
`q1_max=1` 이고 CSV 가 0.75~6.0㎧ 라 **전 구간이 1 로 잘렸다.** 곡률 프로파일이
있으나 마나였다.

속도를 배수로 스케일하는 것도 답이 아니다 — 속도를 k 배 하면 요구 횡가속(v²κ)은
**k² 배**가 되어 어느 코너가 한계인지까지 바뀐다. 코너에 맞추면 직선이 느리고
직선에 맞추면 코너가 터진다.

그래서 속도가 아니라 **마찰 예산**에 η 를 곱한다:

```
a_g = grip_util(η) · μ_eff · g
1) 곡률 한계  v ≤ √(a_g/κ)      CSV 속도는 상한으로만
2) 역방향 패스  다음 코너까지 설 수 있게
3) 전진 패스   낼 수 있는 만큼만
2·3 은 마찰원 결합:  a_lon = a_cap·√(1 − (a_lat/a_g)²)
```

`speed_profile.py` 로 공용화해 map / stanley / gap_follower 셋이 같은 코드를 쓴다.
gap_follower 는 레이싱라인이 없지만 **자기 조향각이 곧 곡률**(κ=tan δ/L)이라
`v ≤ √(a_g/κ)` 로 같은 물리를 적용한다 — "조향 크면 0.6배" 임의 계수를 대체.

검증(halfhot 400점 29.8m, η=0.6): 횡가속 예산 초과 **0/400**, 합성 가속이 마찰원에
정확히 접함(2.35 = 예산 2.35), 최대 가속 +1.29 / 최대 감속 −2.35 가 각 한계와 일치.

`q1_max`~`race_max` 는 삭제. 모드별 위험도는 평평한 상한이 아니라 **`grip_util`
(마찰 예산 사용률)** 로 표현한다.

### 9. "고쳤는데 효과가 없는" 함정이 하루에 세 번

읽는 곳과 쓰는 곳이 갈리면 조용히 무시되면서 고친 것처럼 보인다.

1. `grip_util`/`a_lon_*` 가 `[limits]` 와 `[map]` 양쪽에 존재 → `[map]` 쪽 삭제
2. `map_controller` 가 물리 프로파일을 만든 뒤 **`max_speed` 로 다시 잘랐다** —
   앞선 커밋만으로는 상한이 그대로 살아 있었다
3. 옵티마이저가 `limits.grip_util.**default**` 에 쓰는데 launch 는 **모드 키**를
   먼저 읽는다 → 최적화 결과(0.743)가 통째로 무시되고 0.6 으로 달림
   (`docs/grip_util_shadowing.md`. 노트북에서 모드 키에 쓰도록 수정 완료)

`race_script.yaml` 이 836줄까지 커져 관련 없는 절이 뒤섞여 있던 것도 용도별로
재배치했다(9개 그룹). 값 deep-compare 와 줄 전수 대조로 유실 0 확인.

## 08/06 (젯슨) — MAP 컨트롤러 실차 이식 · 슬립 리그 상한 개방 · Q2 회피 원인 규명

시뮬에서 만든 MAP 컨트롤러를 실차로 옮기고 첫 주행 시험까지 했다. 세 갈래로
문제가 나왔고 전부 원인을 특정했다.

### 1. MAP 컨트롤러 실차 이식

`f1tenth_racing/map_controller_node.py`(시뮬) → `race_stack/map_controller.py`(실차).
**조향·속도 알고리즘은 한 줄도 바꾸지 않았다** — 시뮬에서 Optuna로 튠한 값을 그대로
가져와 실차와 비교하는 게 이식의 목적이기 때문이다. 바꾼 것은 배관뿐:

| 시뮬판 | 실차판 |
|---|---|
| `/ego_racecar/odom` 하나로 pose·속도 | AMCL 보정 ⊕ odom 추측항법 융합 pose |
| 상수 하드코딩 | `race_script.yaml` `[map]` 절 파라미터 |
| `input()` 로 시작 대기 | `/race/enabled` (mission_manager 래치 구독) |
| 속도 클램프 없음 | 모드별 `max_speed`/`min_speed` 로 클램프 |

`controller: map` 으로 다른 컨트롤러처럼 골라 쓴다 (`./race.sh q1 map` 도 가능).
RViz 토픽(`/waypoints_path`, `/waypoint`, `/car_path`)과 `logs/` 주행로그 형식을
stanley·pure_pursuit과 같게 맞춰 `rviz.sh` 를 그대로 쓴다.

또 웨이포인트를 용도별로 갈랐다. 08/05에 생성한 고속 raceline(최대 8 m/s)이
`sohot_clean_wp.csv` 를 덮어써 있었는데, 경로 기하도 구 경로 대비 최대 62cm
안쪽으로 파고드는 다른 라인이었다. 실차 검증 전에 이게 기본값이면 위험하다:

- `sohot_clean_wp.csv` — 구 경로 복원 (최대 4.0 m/s, 검증됨). 기본값
- `sohot_clean_fast_wp.csv` — 08/05 고속 raceline (최대 8.0 m/s)

### 2. MAP 첫 실차 시험 — 버그 두 개

**(a) 출발선에서 안 움직였다.** "정지 중" 로그만 반복되다가, 손으로 조금 밀어주니
그때부터 정상 주행했다. AMCL이 `/amcl_pose` 를 내는 시점은 **(1) 첫 스캔 1회,
(2) 이후 2.5cm/1.7도 이상 움직였을 때**뿐이다. `race.launch.py` 가 컨트롤러를
8초 지연 기동하므로 (1)은 이미 지나갔고, 차가 멈춰 있으니 (2)도 영원히 안 온다:

```
pose 없음 → 0속도 발행 → 안 움직임 → pose 없음  (데드락)
```

stanley는 08/04에 같은 버그를 겪고 고쳐뒀는데, 이식할 때 `pure_pursuit` 구조를
따라가서 그 수정을 안 가져온 것이 원인이다. stanley와 같은 방식으로 맞췄다:
첫 odom이 오면 `init_pose` 에 있다고 **가정하고 시드**하고, 그 뒤로는
`(map←odom 보정) ⊕ (최신 odom)` 으로 50Hz 추측항법. `/amcl_pose` 는 보정 변환만
갱신해 제어 주기와 분리한다.

**(b) 사인파처럼 좌우로 비틀렸다.** L1이 너무 짧은 게 원인이다. 조향각이

```
delta = atan(2 × 휠베이스 × sin θ / L1)
```

인데, 시뮬 최적값 `L1_MIN=0.2725, L1_K=0.275` 를 실차에 그대로 쓰면 1.5 m/s에서
L1 = 0.41m → `atan(1.61·sin θ)` 이라 **방위오차 θ가 13도만 되어도 max_steer가
포화**한다. 시뮬은 pose가 완벽해서 버텼지만 실차는 AMCL 튐만으로 그 13도를
넘나들어 좌우 풀조향이 반복된다. 실차 기본값을 `l1_min 0.90 / l1_k 0.35` 로
올렸다 (같은 13도에서 9.4도). 참고로 Pure Pursuit은 1.8m, Stanley는 0.5~2.5m를
쓰고 있었다 — 0.27m가 얼마나 벗어난 값이었는지 보여준다.

두 수정은 서로 물려 있다. AMCL 원시 pose는 이산적으로 튀는데 그 위에서 짧은
L1로 조향하면 튐이 그대로 조향에 실린다. 50Hz 융합이 입력을 매끄럽게 하고,
긴 L1이 이득을 낮춘다.

장애물 회피는 MAP에 넣지 않았다. Stanley에서 안정화한 뒤 이식한다.

### 3. Stanley Q2 — 두 번째 장애물에서 벽 충돌한 원인

Q2 주행 자체는 잘 됐고 첫 장애물도 잘 피했는데, 두 번째에서 좁은 구역으로
조향해 벽에 부딪혔다. 원인은 `frenet.enabled: false` 라서 **옛 방식(방향 래치 +
고정량)** 이 돌고 있었던 것이다. 이 방식은:

1. 시프트 **방향을 장애물 반대편으로만** 정한다. 그쪽에 트랙이 남았는지 안 본다
2. 시프트 **양이 `car_width + obstacle_margin` = 0.42m 고정**이다. 남은 폭과 무관
3. 한 번 정한 방향을 `lane_free` 가 될 때까지 **래치**한다

half_clean 맵을 실측했다 (맵 자유공간 거리변환 × 웨이포인트 400점):

| 항목 | 값 |
|---|---|
| 라인→벽 여유 | 최소 **0.350m** / 중앙값 0.750m |
| 차 반폭 0.17m 뺀 실제 이동 가능량 | 최소 **+0.180m** / 중앙값 0.580m |
| 0.42m 시프트가 벽을 뚫는 지점 | **69/400점 (17%)** |

**최악 지점에서 0.18m밖에 못 옮기는데 0.42m를 옮기라고 명령한다.** 우연이 아니라
그 17% 구간에 걸리면 방향만 잘못 래치돼도 반드시 벽으로 간다.

→ `frenet.enabled: true` 로 전환. Frenet은 후보 17개를 ±0.60m에 깔고 비용 최소를
고르는데 `bounds: true` 라 트랙 밖 후보가 애초에 배제되고 래치도 없다. 좁은
구간에서는 자연히 작은 오프셋이나 0을 고르고 감속(`obstacle_decel`)으로 처리한다.
파라미터 정합성도 확인했다: `track_margin` 0.28 < 실측 최소 여유 0.350m 라
레이싱라인이 마스크 안에 남고, `w_offset`(1.0) > `w_clear`(0.5) 라 발산이 없다.

### 4. 슬립 리그 — "속도가 안 올라간다" 의 정체는 조용한 거부였다

`slip.speeds` 에 3.0을 적어놔도 실제로는 **2.5로 달리고 있었다.** `joystick_teleop`
가 자기 `max_speed` 를 넘는 요청을 **로그도 없이 버리는데**, 그 `max_speed` 가
`joystick.max_speed`(2.5)였다. 조향도 같은 구조로 `pure_pursuit.max_steer` 를
물려받고 있었다. 즉 리그 상한을 올리려면 자율주행 컨트롤러 상한을 같이 올려야
하는 구조였다.

- **리그 전용 상한 분리** — `slip.max_speed` / `slip.max_steer` 신설.
  전달은 환경변수(`RACE_SLIP_MAX_SPEED/STEER`)로 한다
- 그 과정에서 **`quiet:=true` 가 한 번도 전달된 적이 없었음**을 발견했다.
  `IncludeLaunchDescription` 은 `sys.argv` 를 거치지 않는데 `joystick.launch.py`
  가 argv만 봤다 → 슬립 패널이 다른 노드 출력에 깨지고 있었다. `RACE_QUIET`
  환경변수로 고쳤다

**조향은 좌우가 비대칭이다.** `config/vesc.yaml` 의 서보 매핑
(`servo = -0.761×steer + 0.425`, `servo_min/max = 0.15/0.85`)을 풀면:

- 좌회전 락 **+0.361 rad (20.7도)**
- 우회전 락 **−0.558 rad (32.0도)**

즉 **21도 이상 시험은 우회전으로만 실제 각도가 나온다.** 좌회전으로 돌리면
서보가 0.15에서 잘려 실제는 20.7도인데 기록은 지령값이라 데이터가 조용히 어긋난다.

최종 격자: 속도 `[3, 4, 5, 6, 7]` m/s, 반경 `[0.55, 0.65, 0.74, 0.86, 1.0]` m
(= 31.0 / 26.9 / 24.0 / 21.0 / 18.3도), `max_speed 7.0`, `max_steer 0.55`.

### 6. 시행착오 — 좁은 공간에서 고속 슬립을 하면 안 된다

생각한 게 잘못이었다.

### 7. 주행 로그가 사라지던 두 가지 이유

오늘 로그를 정리하다 **MAP 주행 기록이 하나도 없다**는 걸 발견했다. 45개
폴더가 전부 `_stanley` 였다. 원인이 두 개였고 둘 다 고쳤다.

**(a) 로그가 git repo 밖에 쌓이고 있었다.** `_REPO_ROOT` 가 `RACE_WS` 를 쓰는데
그 값은 실행 워크스페이스(`~/f1tenth_ws`)다. `logs/README.md` 는 "git 으로
커밋해서 공유" 를 전제로 하는데 정작 커밋될 수 없는 자리였다. `__file__` 폴백도
`build/race_stack` 를 거쳐 같은 곳으로 떨어졌다.

→ 경로 규칙을 `race_stack/paths.py` 하나로 모으고 `RACE_REPO`(race.sh 가 자기
위치로 export) → `RACE_SCRIPT` 의 상위 → `RACE_WS` → 파일 탐색 순으로 찾는다.
`slip_logger` 가 따로 계산하던 것도 여기로 합쳤다 — 두 군데서 정하니 실제로
갈려 있었다. (paths.py 는 표준 라이브러리만 쓴다. slip_logger 는 패널만 그리는
가벼운 노드라 경로 하나 얻자고 cv2/scipy 를 끌어오게 하면 안 된다)

**(b) `save_run_log()` 가 애초에 실행되지 않았다.** `main()` 의 종료 처리가

```python
finally:
    node.publish_stop()     # ← 컨텍스트가 닫힌 뒤엔 여기서 예외
    node.save_run_log()     # ← 그래서 여기까지 못 온다
```

였다. `race.sh` 의 `kill_stack` 은 SIGTERM 을 보내고, rclpy 는 그 시점에 이미
컨텍스트를 내린다. 그 뒤 `publish_stop()` 이 `RCLError: publisher's context is
invalid` 를 던져 `finally` 를 뚫고 나가면서 로그 저장이 통째로 건너뛰어졌다.
**stanley 에만 `if rclpy.ok():` 가드가 있어서 그 주행만 살아남은 것**이고,
MAP·pure_pursuit 는 전부 사라졌다. 로그가 남는지가 사람의 종료 방식(Ctrl+C 냐
race.sh 냐)에 달려 있었다.

→ 세 컨트롤러의 종료 경로를 하나로 맞췄다: `ExternalShutdownException` 도 잡고,
발행은 `rclpy.ok()` 로 가드하고, 컨텍스트가 내려간 뒤의 executor 내부 예외는
종료 잡음으로 보고 삼킨다. 가짜 pose 를 먹여 SIGTERM 을 보내는 방식으로
`[run_log] 33점 ... 저장` 까지 확인했다.

## 08/05 (노트북) — MAP 컨트롤러 시뮬 개발 및 파라미터 최적화

### gym 동역학 모델 재해석

`v_switch = 7.319 m/s`를 "KS↔ST 전환점"으로 잘못 알고 있었다. 실제로는 **종방향
가속도 상한**만 조정하는 값이다:

```
v > v_switch → pos_limit = a_max * v_switch / v  (고속 구동력 제한)
v ≤ v_switch → pos_limit = a_max
```

gym은 **항상 `vehicle_dynamics_st`만 호출**하고, 타이어 횡력(`C_Sf=4.718,
C_Sr=5.4562`)은 전 속도에서 동일하게 작용한다. Pacejka 슬립 보정은 저속에서도
유효하다.

### Pacejka ↔ gym 정합

gym ST는 선형 타이어: `F_yf = μ · C_Sf · Fzf · α`

Pacejka 소각도 기울기: `Fy_norm ≈ B·C·D · α`

두 식을 같게 하면: `BCD = C_Sf = 4.718`

```
PAC_B = C_Sf / (C × D) = 4.718 / (1.3 × 1.0) = 3.629
```

기존 PAC_B=10이었을 때 BCD=13, 즉 **슬립각을 2.8배 과소추정**해 보정이 항상
부족했다. `MAX_STEER`도 gym `s_max=0.4189`에 맞춰 수정.

### TUMFTM 최소곡률 레이싱라인 생성기

trajectory_planning_helpers가 Jetson Python 환경과 충돌해 직접 재구현
(`gen_raceline.py`):

- 맵: sohot_clean.pgm → cv2 윤곽 추출 → 중심선 → 법선벡터
- QP: `min ½α'Hα + f'α` (OSQP), 제약 = 트랙 폭 경계
- 결과: 417점, 41.7m, 속도 2.88~8.00 m/s

### MAP 파라미터 자동 최적화 (Optuna + gym)

`optimize_map_params.py` — 300 trials, 10분:

| 파라미터 | 기존 | 최적 | 비고 |
|---|---|---|---|
| L1_MIN | 0.45 | **0.2725** | |
| **L1_K** | **0.12** | **0.275** | 핵심: 8m/s 예견거리 0.96→2.2m |
| STEER_ALPHA | 0.35 | **0.198** | 필터 완화 |
| A_BRAKE | 9.47 | **6.09** | 조기 감속 |
| PAC_D | 1.0 | **1.208** | 마찰 스케일 미세 조정 |

결과: 미완주 → **완주 6.88초**. L1_K가 핵심 — 기존 0.12는 고속에서 예견거리가
너무 짧아 코너 반응 자체가 불가능했다.

## 08/05 (밤) — 타이어 슬립 데이터 수집 리그

고속 주행의 최종 목표가 "슬립까지 활용하는 것" 이라, 실차 슬립 데이터로 타이어
모델을 세우고 → MAP 하이브리드 컨트롤러 → 시뮬 기반 경로 생성기로 가는 계획.

### 순서를 하나 바꿨다 — 수집에는 자율주행이 필요 없다

계획대로면 슬립 데이터를 얻으려 2.5 m/s 로 달려야 하고, 그러려면 컨트롤러·
위치추정·레이싱라인이 먼저 멀쩡해야 한다. 지금 셋 다 미완이라 그 속도에서
데이터를 모으기 전에 박는다.

그런데 정상원·스텝 스티어는 **조이스틱 수동 주행으로 가능**하다. IMU + 휠
오도메트리 + 서보 명령만 있으면 되고 AMCL 도 Stanley 도 안 쓴다. 지금 막힌
것들과 분리해 바로 시작할 수 있다.

### 슬립은 생각보다 가깝다

우리 트랙 최급코너(κ 1.14) 기준:

| 속도 | a_y | μ0.7 한계 대비 |
|---|---|---|
| 1.5 ㎧ (현재) | 2.6 ㎧² | 37% |
| **2.0 ㎧** | 4.6 ㎧² | **66% ← 슬립 시작권** |
| 2.5 ㎧ | 7.1 ㎧² | 103% (초과) |

5~7 ㎧ 까지 갈 필요가 없다. **지금보다 33% 빠르면 슬립 영역**이다.

### 주 지표를 β 적분이 아니라 언더스티어 구배로

요청받은 관측기 β̇ = a_y/v − ψ̇ 는 수식이 맞지만 우리 하드웨어에 불리하다:
IMU 가 50 Hz 이고(vesc_driver.cpp:107 의 20ms 폴링 타이머 탓, 센서 한계 아님),
타임스탬프가 샘플 시각이 아니라 패킷 파싱 시각(같은 파일 :211 의 `now()`)이라
지터가 적분에 쌓인다.

그래서 적분이 필요 없는 정상상태 관계를 주 산출물로 삼았다:

```
δ = L·ψ̇/v + K_us·a_y   →  (δ − L·ψ̇/v) 를 a_y 로 회귀 = K_us
```

합성 데이터 검증: 주입 K_us 0.010/0.025/0.050 을 오차 0.0005 이내로 복원,
K=0 일 때 R² 0.019 로 없는 기울기를 지어내지 않음.

### 시험법 — 정조향 램프 (바닥 표시 불필요)

"바닥에 반경별 원을 그려야 하나" 라는 질문에서 시험법을 다시 봤다. 회귀에 쓰는
δ·ψ̇·v 를 **전부 측정**하므로 반경은 목표가 아니라 결과다. 차가 실제로 그린
원이 1.0m 든 1.23m 든 회귀는 동일하게 성립한다.

그래서 "원을 따라가며 핸들 조정" 대신 **"스틱을 고정하고 속도만 올림"**:
· 사람이 훨씬 쉽게 재현한다
· 정상상태 판정의 "δ 변동 < 2°" 가 자동 만족된다 (스틱을 안 움직였으니)
· 슬립이 생기면 차가 저절로 벌어지고, 그 벌어짐이 곧 슬립량이다

### 조작 — 두 스틱 모두 "끝까지 = 시험값"

slip_logger 가 시험 조향각과 목표 속도를 joystick_teleop 에 상한으로 넘긴다.

```
←→  L스틱 최대각 (반경 1.0m → 18.3°)
↑↓  RT 최대속도
B   시작 / 종료
```

**미세 조작이 필요 없다.** 특히 RT 는 분해능 문제가 실재했다 — max_speed 2.5㎧
에서 트리거 1% 가 0.025㎧ 이고 사람이 ±5% 로 잡으면 ±0.125㎧ 라, 정상상태
허용치(0.15㎧)와 거의 같아 표본이 잡힐락 말락 했다. 상한을 목표로 낮추면 같은
트리거 행정이 그만큼 정밀해진다.

안전: teleop 은 `min(설정값, 받은값)` 으로만 쓴다 — 오버라이드가 상한을 **올릴
수는 없다**. 1초 타임아웃이라 slip_logger 가 죽어도 조종은 정상이다.

`ros2 run` 으로 실제 기동 확인 — 패널 정상. jstest 로 F710 매핑 실측:

1. D-pad **부호** — 리눅스 규약은 Hat0Y 위=-1 인데 ROS joy_node 가 뒤집는지
   확인 못 했다. 화면에 raw 값을 띄우고 `slip.dpad_*_invert` 로 뒤집게 해 뒀다
2. **가속도 축 부호** — 전방=-y/좌측=+x 는 기울여서 잰 값이라 실제 횡가속도로
   검증된 적이 없다. 좌회전에서 a_y 가 + 로 나오는지 확인할 것
3. 전체 스택 연동 — 화면 "연결" 줄 4개가 다 ✔ 면 배선 정상

### 첫 회에 제일 중요한 확인

낮은 속도(1.0㎧)에서 `실제/기구학` 이 **1.00 근처**인가. 처음부터 0.9대면
슬립이 아니라 **조향 캘리브레이션 문제**이고, 그 상태로는 데이터를 아무리
모아도 K_us 가 캘리브레이션 오차와 섞여 못 쓴다.

## 08/05 (밤) — 맵 스케일 종결 + 위치추정 계측기 도입

### ★ 맵 스케일 문제 종결 (08/02 부터 미해결이던 항목)

줄자 실측과 맵이 일치한다. **스케일은 정상이다.**

```
맵이 말하는 트랙(자유공간)  14.15 x 6.60 m
줄자 실측                  14.5  x 6 m 조금 안 됨
```

※ 한동안 "맵 33.1 x 9.3 m" 로 알고 있었는데 그건 **맵 이미지 전체 크기**였다.
   트랙은 그 안의 자유공간이다. 이 혼동이 스케일 의심을 키웠다.

래스터 맵은 해상도가 하나뿐이라 축마다 다른 배율이 나올 수 없다. 두 축 모두
맞으므로 스케일 오류는 배제된다.

### localization_monitor 도입 — 위치추정 품질을 숫자로

매 스캔마다 "이 자세가 맞다면 라이다는 뭘 봐야 하는가" 를 맵 레이캐스팅으로
구해 실측과 비교한다. 읽기 전용이라 주행에 영향이 없고, 어떤 필터(AMCL·SynPF)
를 쓰든 같은 잣대다 — 필터 교체 효과를 재는 유일한 근거가 된다.

**첫 실측 (20260805_195922, q1 3랩):**

```
정지 상태 잔차   평균 19.7cm  중앙 17.8cm  90% 42.6cm
주행 자체는 건강  |cte| 8.0cm, 랩 20.49/20.86/20.76s (편차 0.4%)
```

맵이 정확하다는 것이 확인됐으므로 이 20cm 는 **위치추정 오차**다. 라이다 잡음·
맵 5cm 양자화·벽 두께로 5cm 정도가 바닥값이니 실제 자세 오차는 15cm 안팎이다.
이 트랙은 레이싱라인에서 벽까지가 36cm 이므로, **여유의 40% 를 위치추정이
먹고 있다.** 벽 오검출·트랙 좌우 요동의 뿌리가 여기다.

### 맵 스케일 판정 기능은 만들었다가 **뺐다**

"잔차가 거리에 비례해 자라면 스케일 오류" 로 판정하려 했으나, 실측 자세로
검증한 세 추정기가 전부 실패했다.

| 추정기 | 결과 |
|---|---|
| \|잔차\|~거리 회귀 | 정지 상태인데 창마다 -16% ~ +7% 로 부호 뒤집힘 |
| 원점통과 비율 회귀 | 부호는 맞으나 자세 오차 20cm 에 ±2~5% 가짜 신호 |
| 자세+스케일 동시 최적화 | +3% 주입 → -5% 추정. 그런데 **잔차 0.1cm** |

마지막이 원인을 말한다. 긴 복도에서는 스캔을 확대·축소한 뒤 옆으로 밀면 같은
벽에 맞는다 — **스케일과 자세가 기하학적으로 분리되지 않는다**(aperture problem
의 스케일 판). 알고리즘이 아니라 관측 기하의 한계다.

틀린 값을 확신에 차서 출력하는 건 없느니 못하므로 제거했다.
**맵 스케일은 줄자가 정답이다** — 실제로 그렇게 닫혔다.

### 잔차 공간분포 — 어느 벽이 옮겨졌는지 찾는다

맵을 만든 뒤 주행 테스트 중 차가 벽 구조물을 들이받아 실제 벽이 조금씩
옮겨졌다(사용자 확인). 그러면 필터를 아무리 좋게 만들어도 **틀린 답에 정확히
수렴할 뿐**이다. SynPF 도입보다 이게 먼저다.

자세 오차라면 모든 빔이 고르게 틀리지만, 벽이 옮겨졌다면 **그 벽을 보는 빔만**
크게 틀린다. 잔차를 위치별(0.4m 격자)로 모아 상위 5칸 / 중앙값 비를 본다.

**오프라인 교정 (자세 오차 15cm 를 함께 준 상태):**

```
벽 정상       비 1.6배 → 자세 오차     (정답)
벽 10cm 이동  비 1.6배 → 자세 오차     ← 못 잡는다 (자세 오차에 묻힘)
벽 20cm 이동  비 2.2배 → 국소 불일치   좌표도 정확히 지목 (+7.8,+2.2)
벽 40cm 이동  비 3.6배 → 국소 불일치
```

실측 로그의 **중앙값 17.8cm vs 90% 42.6cm** 라는 두꺼운 꼬리가 이미 국소
불일치를 시사한다. 다음 주행의 `[map]` 줄로 확정한다.

### 오독 정정

"AMCL 이 정지 상태에서 0.5m 배회한다" 고 적었으나, 로그를 다시 보니 사용자가

클릭이 없던 구간의 잔차는 19.7cm 로 안정적이었고, 그 값이 진짜 지표다.

※ 정정: "nav2_amcl 은 느리다" 는 우리에게 맞지 않는다. 우리 AMCL 은

## 08/05 (저녁) — 벽 오검출을 빔별 기대거리 비교로 해결

**증상:** q2 로 달리면 장애물이 없는 직선 9.4m 를 레이싱라인에서 **42cm 옆으로
평행하게** 밀려서 달린다. 진동이 아니라 일정한 오프셋이다 (부호변화 21m 에 4회).

```
20260805_182240_q2  직선 x 1.3~10.7m
  cte  -40 ~ -45cm 로 거의 고정
  같은 구간 q1(182155) 평균 -4.8cm
```

**원인 확정:** 수치가 정확히 맞아떨어졌다.

```
obs_shift = car_width + obstacle_margin = 0.30 + 0.12 = 0.42 m
관측된 상시 횡변위                       = 0.42 m
```

차가 직선 내내 "경로가 막혔다" 고 판정하고 회피 시프트를 최대치로 물고 있었다.
게다가 `_shift_side` 는 래치라 `lane_free` 가 True 가 될 때까지 안 풀린다 —
벽이 계속 잡히니 영영 안 풀렸다.

즉 08/05 오전에 다룬 **벽 오검출이 그대로 남아 있었다.** 마스크 방식
(`track_margin`) 은 "이 반사점이 맵 벽에서 margin 이상 떨어져 있는가" 만 보므로,
AMCL 오차가 margin 을 넘는 순간 벽 반사가 그대로 장애물이 된다. margin 을 키우면
라인 위 최소 여유(이 트랙 36cm)를 넘어 라인 자체가 마스크 밖으로 나간다. 즉
**구조적으로 막다른 길이었다.**

### 해결 — 빔별 기대거리 비교 (레이캐스팅)

판정 질문을 바꿨다.

| | 질문 | 실패 조건 |
|---|---|---|
| 마스크 (구) | 이 점이 벽 근처인가? | AMCL 오차 > track_margin |
| 레이캐스팅 (신) | 이 빔이 맵 벽보다 앞에서 끊겼는가? | AMCL 오차 > pose_unc + deficit |

핵심은 **맵의 벽을 위치추정 불확실성 반경만큼 부풀린 뒤** 레이캐스팅하는 것이다.
그러면 기대거리가 "불확실성 안의 **어떤** 위치에서든 가능한 가장 짧은 거리" 가
된다. 실측이 그보다도 더 짧으면, 그 반사는 어떤 위치를 가정해도 맵 벽으로 설명할
수 없다 → 진짜 장애물이다.

대가는 **벽에 바짝 붙은 장애물을 놓치는 것**이다. 반대 방향의 오류(벽을 장애물로
봄)는 직선 9m 를 42cm 밀려 달리게 만들었으니 이쪽 대가가 훨씬 싸다.

### 검증 (half_clean 맵 + 실주행 자세 107개, 합성 스캔)

벽만 있는 스캔에 AMCL 오차를 인위로 주고 "벽을 장애물로 오인한 빔" 비율:

| AMCL 오차 | 마스크 (0.28) | 레이캐스팅 (unc 0.25) |
|---|---|---|
| 0.20m | 0.00% | 0.00% |
| **0.30m** | **23.10%** | **0.80%** |
| 0.40m | 41.57% | 6.50% |
| 0.60m | 58.75% | 16.34% |

진짜 장애물(지름 0.51m 원기둥, 오차 0.20m) 탐지율 — 프레임당:

| 장애물 위치 | 마스크 | 레이캐스팅 |
|---|---|---|
| 라인 중앙 | 100% | 93% |
| 라인에서 20cm 옆 | 100% | 93% |
| 벽 쪽 40cm | 100% | 88% |

프레임당 88~93% 는 `obs_vote_frames: 7` 과반 판정에서 사실상 100% 가 된다.
연산은 **1.7ms/스캔** (라이다 40Hz = 25ms 예산).

### 구현 메모

- `_build_raycast_map()` — 기동 시 1회. 맵 점유를 `raycast_pose_unc` 만큼 dilate.
- `_raycast_expected()` — 전 빔을 B×S 배열로 한 번에 행진 (파이썬 루프 없음).
- `_raycast_obstacle_pts()` — `meas < expected - deficit` 인 빔만 map 좌표로.
- `_scan_cb` 는 `ray_occ` 가 있으면 격자+마스크 경로를 건너뛴다.
  `raycast_obs: false` 로 두면 예전 방식으로 되돌아간다.

**엣지 케이스 (검증 중 발견, 수정함):** 차가 벽에서 `pose_unc` 이내에 있으면
광선 **시작점이 부풀린 벽 안쪽**이라 모든 빔이 t=0 에서 명중 → 기대거리가 전부 0
→ 장애물 탐지가 통째로 멎는다. 트랙 여유 36cm 에 부풀림 25cm 라 실제로 자주
일어난다. 광선이 일단 자유공간으로 빠져나온 뒤부터 명중을 세도록 고쳤다.

```
벽까지 거리   수정 전 기대거리   수정 후
   0.30m         1.73m         1.73m
   0.20m         0.00m  ←멎음   1.58m
   0.10m         0.00m  ←멎음   1.53m
```

### 부수 효과

Frenet 의 clearance 계산이 쓰는 `on_track_pts` 에서도 벽이 빠진다. 전에 지적된
"clearance 를 `on_track_pts` 로 재면 벽이 들어가지 않느냐" 는 문제가 같이 해결된다.

### 남은 것

- 실차 검증 (아직 안 함)
- 벽 밀착 장애물 대응이 필요하면 스캔 공간 "양옆 분리성" 판정을 OR 로 추가

## 08/05 — 조향 한계를 넓혔다가 직선에서 발산

**증상:** `max_steer` 0.36 → 0.40 / `servo_min` 0.15 → 0.11 적용 후, q1 직선에서
횡오차가 반주기마다 커지며 발산했다.

```
20260805_174627  직선 구간
  -20 → +18 → -27 → +38 → -65cm   (진폭 ×1.4~1.9 씩 증가)
  헤딩 ±50° 요동, 공간주기 1.3m (6.9 rad/s)
```

**AMCL 문제가 아니다** — 위치 로그가 완전히 연속적이었고 (dt 0.098s 균일, 헤딩
점프 0건, 위치 점프 1건=출발 시) 실제 차량 진동이었다.

**원인:** `gain 1.6` 은 그 자체로 불안정한데 `max_steer 0.36` 포화가 유일한
감쇠원이었다. 한계를 11% 넓히자 감쇠가 사라져 발산했다.

선형 모델로는 진동이 안 나온다 (ωn 2.49 rad/s, ζ 1.41 = 과감쇠). 관측된 6.9 rad/s
는 비선형·지연 성분이다.

**시행착오:** 처음엔 같은 커밋에 있던 `offset` 0.425 → 0.419 (조향 중립 실측값)
를 의심해 백래시 가설을 세웠으나, 되돌려도 발산이 그대로여서 기각했다.

**조치:** 3개 값을 모두 되돌려 정상 주행 복귀를 실차로 확인.

**교훈:** 조향 여유를 넓히려면 **게인 안정화가 선행**되어야 한다
(`gain 1.6 → 1.2`, `steer_lpf 1.0 → 0.6`). 순서가 반대였다.

### 조향 실측 기록 (되돌렸지만 값은 유효)

```
좌 기구 스토퍼  서보 0.100 = +24.02°     실측 중립 서보 0.419
우 기구 스토퍼  서보 0.860 = -33.20°     현재 설정 0.425
기구 가동범위 중점 0.480 vs 참 중립 0.419 → 링키지가 4.6° 우측으로 치우침
```

대칭 링키지 가정이 틀렸다. 타이로드로 중립을 0.48 쪽으로 옮기면 좌우 ±28.6°
(κ 1.65) 가 되지만, 그 전에 게인 안정화가 필요하다.

### 레이싱라인 곡률 vs 차량 한계 (max_steer 0.36 기준)

```
물리 한계          κ 1.14 (반경 0.88m)
ff_gain 1.2 포화   κ 0.94 (반경 1.07m)  ← 실질 한계
레이싱라인 최대     κ 1.78 (반경 0.56m)  ← 못 돈다
```


## 08/05 — 장애물 없이도 사인파로 진동하던 것

**증상:** q2 로 달리면 트랙 좌우로 규칙적으로 요동친다. 장애물을 **전부 치우고**
돌려도 같았다.

```
장애물 없는 q2 주행 (20260805_160145)
  27.1초 / 39.1m / 평균 1.43 m/s
  횡오차 평균 26.7cm / 최대 88.0cm
  영교차 20회 → 파장 3.95m, 주기 2.76s
  하단 직선 구간 진폭 66cm (peak-to-peak)
  위치 점프 4건 (최대 29cm)
```

**추론:** 코드상 장애물이 하나도 감지되지 않으면 `goal = 0` 이라 시프트가 아예
안 걸린다. 그런데 장애물이 없는데 진동한다 → **지금도 벽이 장애물로 잡히고 있다.**

레이싱라인 자체의 문제도 아니다 — 직선 구간에서 라인의 직선 피팅 잔차가
RMS 5.8cm / 최대 14.4cm 로, 관측된 진폭 66cm 를 설명하지 못한다.

**원인:** 08/04 에 넣은 트랙 마스크는 `track_margin` (당시 0.20m) 만큼 벽에서
떨어진 곳만 "트랙 안" 으로 본다. 오프라인 검증은 **완벽한 pose** 를 가정했기에
0개가 나왔지만, 실차에서는 AMCL 오차가 그 여유를 잡아먹는다. 이 주행만 해도
위치 점프가 4건(최대 29cm)이다. 오차가 여유를 넘으면 벽 반사가 마스크를 통과하고,
그것이 간헐적으로 들락날락하며 시프트를 켰다 껐다 해서 사인파가 된다.

**조치**
- `track_margin` 0.20 → **0.28** (yaml 노출). 라인 위 최소 여유 36cm 보다는
  작아야 라인이 마스크 안에 남는다 — 이 트랙에서 쓸 수 있는 상한이 그 정도다
- `obs_vote_frames` 3 → **7**. 단발 오검출이 과반을 못 넘기게 해 깜빡임을 막는다

**★ 구조적 한계 (다음 세션 과제)**

이 트랙은 **복도 폭 대비 위치 오차가 크다**. 마스크 여유는
`AMCL 오차 < track_margin < 라인 여유(36cm)` 를 만족해야 하는데, 오차가 30cm 에
육박하면 그 창이 거의 없다. 값 조정으로는 한계가 있다.

제대로 된 해법은 **빔별 기대거리 비교**다 — 현재 pose 에서 맵이 예측하는 각 빔의
거리를 구하고, 실측이 그보다 **뚜렷하게 짧을 때만** 장애물로 본다. 벽 반사는
기대거리와 일치하므로 위치가 복도를 따라 어긋나도 벽으로 남는다. 지금의
"맵 위 어디에 찍혔나" 방식보다 위치 오차에 훨씬 강하다.

## 08/04 — 회피 알고리즘 개편 + 출발 절차 자동화 + "안 움직임" 원인 규명

08/03 에 IMU yaw 를 넣었으니 그 위에 올릴 것들과, 대회 운용에 필요한 절차를 붙인 날.
**전부 오프라인 검증까지다. 실주행 검증은 아직 하나도 없다.**

### 1) Frenet 후보 궤적 회피 — 고정량 시프트를 대체

**기존:** "막혔다" → 래치한 한쪽으로 **고정량**(`car_width + margin` = 0.42m) 이동.
장애물 폭·위치와 무관하게 늘 같은 양을 같은 쪽으로 밀었다. 그쪽이 더 좁아도,
살짝만 비켜도 되는 상황에도 똑같이.

**변경:** 레이싱라인을 기준선(s축)으로 삼고 **횡오프셋 후보 9개**(±0.6m)를 깔아,
각 후보 경로가 장애물·트랙경계에서 실제로 얼마나 떨어지는지 재서 고른다.

```
비용 = w_offset·|d| + w_change·|d−현재| − w_clear·min(여유, clear_cap)
       라인 복귀력     히스테리시스        여유 보상(상한 있음)
```

**검출 파이프라인은 손대지 않았다.** 통로 판정(`obs_corridor_half_width`)·투표·
슈미트 트리거는 실차에서 튜닝된 자산이라 그대로 두고, **"얼마나 어느 쪽으로"만**
교체했다. 바꿀 범위를 좁히는 게 실차 회귀를 막는 유일한 방법이다.

**방향 래치가 사라졌다.** 연속성은 `w_change` 비용이 만든다. 그래서 좌우 양쪽에
장애물이 있으면 가운데를 고르는 판단이 자연히 나온다 — 예전 구조로는 불가능했다.

검증(실제 sohot 웨이포인트 + 트랙 마스크):

| 상황 | 결과 |
|------|------|
| 장애물 없음 | d=0 (라인 유지) |
| 정중앙 | 0.30m 회피 |
| 좌측 0.3m | 우측으로 회피 |
| 좌우 양쪽 0.55m | **가운데 유지** |
| 폭 0.4m 장애물 | 0.60m (폭 비례) |
| 성능 | **1.54ms/호출 = 50Hz 주기의 7.7%** |

> ★ **검증 중에 설계 버그를 하나 잡았다.** 검출은 통로 반폭 0.30 으로 "막혔다" 고
> 판정하는데 Frenet 은 요구 여유 0.25 로 "라인 그대로도 괜찮다" 고 답해서,
> **막혔다고 해놓고 아무 회피도 안 하는 상태로 굳었다.** 두 층이 다른 기준을 보면
> 이렇게 된다. 기본값을 0.35 로 올리고, 통로 반폭보다 작게 넣으면 노드가 경고 후
> 승격하도록 했다. 실차에서 만났으면 원인 찾기 매우 어려웠을 종류다.

RViz `/frenet_candidates` — 초록=선택, 파랑=가능, 빨강=불가.

### 2) 스캔 모션 보정 (LiDAR deskewing)

라이다 한 스캔(40Hz → 25ms) 동안 차가 움직이면 첫 빔과 마지막 빔이 **서로 다른
위치에서** 찍힌 것인데 메시지는 같은 순간처럼 담긴다 → 점군이 찌그러진다.

```
코너에서 ω=2rad/s → 스캔 도중 2.9° 회전 → 5m 거리의 점이 25cm 어긋남
```

AMCL 의 likelihood field 가 이 찌그러진 점을 맵에 억지로 맞추려다 위치가 튄다.
**속도에 정확히 비례해 나빠지므로**, 최고속을 올리기 전에 미리 넣었다.

빔별 시각 `t0 + i·time_increment` 로 자세를 보간해 되돌리고 원래 각도 격자에
재배치한다(같은 칸이면 가까운 쪽을 남겨 보수적으로). 정지·저속에서는 원본을
그대로 통과시킨다 — 보정량이 노이즈보다 작으면 재배치가 오히려 점을 흩뜨린다.

검증(합성 스캔): 균일 3.0m 원은 회전 불변 유지, **정면 벽 기울기 +0.0252 → −0.0013**
(19× 개선), 정지 시 원본 그대로 통과.

> ⚠ `deskew_stamp_at` 이 틀리면 보정이 **반대로** 걸려 오히려 나빠진다.
> urg_node 기준 `start` 로 뒀지만 실차에서 확인 필요.

### 3) 컨트롤러·AEB 를 `/odom_imu` 로

`stanley_controller`·`safety_node`·`pure_pursuit` 모두 `odom_topic` 파라미터화
(기본 `/odom_imu`). 진로 원호 예측 `R = v/ω` 이 yaw rate 에 걸려 있어서,
서보 명령 기반 ω 로는 **실제보다 많이 휜 통로**를 보고 장애물·AEB 를 판정했다.
이제 위치추정뿐 아니라 회피 판정까지 자이로 실측을 쓴다.

### 4) "로그는 정상인데 차가 안 움직임" — 구조적 데드락

실차에서 스택이 전부 정상 기동했는데 차가 가만히 있었다.

`_cmd_tick` 은 `_current_pose()` 가 None 이면 0속도를 발행하는데, 그 값은
**`/amcl_pose` 를 한 번이라도 받아야** 채워졌다. 그런데 AMCL 이 `/amcl_pose` 를
내는 시점은 (1) 첫 스캔 1회, (2) `update_min_d` 2.5cm / `update_min_a` 1.7° 만큼
움직였을 때뿐이다. `race.launch.py` 는 lifecycle 을 5초, 컨트롤러를 8초로 지연
기동하므로 **(1) 이 컨트롤러가 뜨기 전에 끝나 있다.** 래치 토픽도 아니라 놓치면
끝이고, 차가 멈춰 있으니 (2) 도 영원히 안 온다.

```
실제 로그: amcl createLaserObject 293.72  /  controller ready 298.99  (5.2초 차)
```

→ **"pose 가 없어 0속도 → 안 움직이니 pose 도 안 옴"** 데드락.

**수정:** 첫 odom 이 오는 순간 `init_pose`(= AMCL 이 파티클을 뿌린 그 값)에 있다고
가정해 map←odom 보정을 시드한다. 둘의 가정이 같으므로 모순이 없고, 진짜
`/amcl_pose` 가 오면 즉시 덮어쓴다. **기다림에 주행을 걸지 않는 것이 핵심이다.**

정지 상태일 때 이유를 3초 스로틀로 로그하게 했다(`enabled=false` / 웨이포인트 없음 /
pose 없음). 같은 증상을 다시 겪지 않기 위한 것이다.

### 5) 출발 절차 자동화 — 대회 운용

세 개가 맞물린다.

**(a) `auto_localize` — RViz 클릭을 코드가 대신한다**

AMCL 은 `recovery_alpha=0` 이라 `init_pose` 주변에만 파티클을 뿌리고, 정지 상태에서는
필터를 갱신하지도 `/amcl_pose` 를 내지도 않는다. 그래서 지금까지는 RViz 에서
`2D Pose Estimate` 를 사람이 찍어야 정렬이 됐다 — **대회 출발선에서 노트북 열고
클릭하는 건 현실적이지 않다.**

맵의 거리변환장을 만들고 → `init_pose` 주변 ±0.5m ±15° 를 5cm·1° 격자로 훑으며
→ 각 후보에서 스캔 점들이 맵 벽에 얼마나 붙는지 평균 거리로 점수화 → 최적 자세를
`/initialpose` 로 발행. AMCL 이 즉시 재시드하고 `/amcl_pose` 를 낸다.

yaw 마다 한 번 회전시키고 xy 는 브로드캐스트로 훑어 벡터화 — 후보 약 9천 개를
0.1초 안에 평가한다. 공분산은 격자 크기만큼 남긴다(0 이면 파티클이 한 점에 몰려
이후 보정이 둔해진다).

검증(`half_clean` 실제 맵 + 라이다 노이즈 3cm): init 오차 7~64cm / 1~13° 를 주고
전부 복원, **최대 위치오차 3.6cm 0.0°**.

> 전역 위치추정이 아니다. `init_pose` 근처만 찾는다. 탐색을 넓히면 좌우 대칭이
> 강한 트랙에서 뒤집힌 자세가 비슷한 점수를 낼 수 있어 기본값을 좁게 뒀다.

**(b) 출발 게이트 + 준비 완료 판정**

기동에 8초가 걸려 출발 신호를 듣고 실행하면 늦는다. `mission.start_gate: true` 면
`/race/enabled=false` 로 잡아두고 트리거를 기다린다 — 터미널 Enter / 조이스틱
버튼 / `./race.sh go`.

> Enter 처리에 함정이 있다. `ros2 launch` 로 띄운 노드는 **stdin 이 터미널이 아니라
> `input()` 이 안 된다.** 제어 터미널이 살아 있으면 `/dev/tty` 는 열리므로 그쪽을
> 직접 읽는다. tty 가 없으면(tmux·`jetson.sh`) 조용히 포기하고 나머지로 폴백한다.

"노드가 떴다" 와 "출발해도 된다" 는 다르다. **셋을 다 확인**한다:
정렬 완료(`/race/localized`) + AMCL pose 수신 + 컨트롤러가 `/drive` 발행 중.
다 되면 배너를 한 번 크게 띄우고, 안 되면 남은 항목을 2초마다 찍는다.
미준비 상태에서 버튼을 누르면 막고 무엇이 빠졌는지 알린다 — 다만 대회에서 못
나가는 게 최악이므로 **3초 안에 다시 누르면 강행**한다.

랩타임·제한시간을 기동 시각이 아니라 **출발 시각**부터 세도록 고쳤다.

**(c) 대회 절차가 이렇게 정리된다**

```
출발선(= 맵 원점)에 차를 놓는다   ← cm 단위로 맞출 필요 없음
./race.sh q2                      ← 미리 실행
   정렬 결과: (+0.02, −0.03)  평균오차 2.1cm
   ╔══ 출  발  준  비  완  료 ══╗
(출발 신호) → 조이스틱 B          ← 즉시 출발
```

RViz 도 노트북도 필요 없다.

### 6) LB = 주행 중 수동 개입 스위치

**증상:** `./race.sh joy` 에서 LB 로 자율 전환하면 로그는 뜨는데 차가 안 움직임.

**원인:** joy 모드는 브링업+조이스틱만 띄운다 — `/drive` 를 내는 컨트롤러가 없다.
자율 모드란 "`/teleop` 발행을 멈춰 mux 를 `/drive` 로 넘기는 것" 뿐이라, 넘길
대상이 없으면 아무 일도 안 일어난다.

**정리:**
- `./race.sh joy` — LB 토글 **제거**. 눌러도 무시하고 왜 꺼졌는지 알린다
- `./race.sh q1|q2|q3|race` — `joystick_teleop` 을 주행 스택에 붙이고 자율로 시작.
  LB 를 누르면 컨트롤러가 멈추고 사람이 조종한다. **AMCL·LiDAR·맵은 그대로 살아
  있어 위치 추정이 끊기지 않으므로, 다시 누르면 그 자리에서 자율주행이 이어진다.**
  트랙 이탈 복귀·회수용

`/race/enabled` **소유권을 정리했다.** `joystick_teleop` 이 직접 쓰지 않고
`/race/manual`(래치)로 "사람이 개입했다" 는 사실만 알린다. `mission_manager` 가
유일한 주인으로서 출발 게이트·랩 완주 정지와 함께 해석한다. 한 토픽을 두 노드가
쓰면 마지막에 쓴 쪽에 따라 상태가 뒤집힌다.

자율인데 `/drive` 가 1.5초 넘게 안 오면 경고한다 — 다시는 조용히 실패하지 않도록.

### 7) DDS 모드 불일치 함정

공유기 교체 후 젯슨만 새 대역으로 바꾸자 노트북 RViz 가 먹통이 됐고, **옛 값으로
되돌리니 다시 됐다.** 옛 IP 가 맞아서가 아니라 **설정이 꺼져서** 된 것이다.

### 10) 초기 정렬을 복도 벽 방향으로 (yaw 재현성)

(d) 의 근본 대책. 출발 지점은 양옆이 벽인 **직선 복도**다. 복도에서 비용 함수는
복도를 따라서는 평평하고(aperture problem) yaw 도 1° 격자로는 잘 안 갈린다.
그런데 **벽의 방향 자체가 답을 알려준다** — 격자 탐색으로 짐작할 이유가 없다.

구현에서 두 번 막혔고, 둘 다 "무엇을 보는가" 의 문제였다.

1. **스캔 쪽**: 처음엔 인접점 차분으로 방향을 냈는데 집중도가 0.14 였다.
   라이다 빔 간격이 1m 에서 5.8mm 인데 거리 노이즈가 3cm 라 **노이즈가 방향을
   완전히 지배**한다. → 좌·우 벽을 각각 **직선 피팅(PCA)** 하니 0.98 이 됐다.
   360° 전체가 아니라 옆쪽(전방축 50~130°)의 가까운 점만 쓴다 — 코너·안쪽 섬이
   섞이면 방향성이 희석된다.
2. **맵 쪽**: 장애물 픽셀 전체로 PCA 하면 0.26 이었다. 맵의 벽은 **속이 채워진
   두꺼운 덩어리**라(이 맵은 아래 1m·위 3.2m) 뭉치를 보게 된다. 라이다는
   **표면만** 보므로 맵에서도 표면(자유공간에 닿은 장애물 픽셀)만 쓰고, 각 점의
   국소 방향을 Sobel 법선에서 얻어 히스토그램으로 모았다 → 178.9° (집중도 0.52).

벽 방향은 **정답이 아니라 사전값**으로 쓴다 — 그 주변 ±6° 를 격자로 마저 훑는다.

검증(합성 스캔 + 라이다 노이즈 3cm):

| init_yaw 오차 | 벽 정렬 OFF | 벽 정렬 ON |
|---|---|---|
| ±0 / 8 / 12° | yaw 0.00°, 5.0cm | yaw 0.53°, 5.0cm |
| +20° | yaw 5.00°, 11.2cm | yaw 0.53°, 5.0cm |
| **-25°** | **yaw 10.00°, 67.3cm** | **yaw 0.53°, 5.0cm** |

`init_yaw` 가 탐색 범위(±15°)를 벗어나도 **항상 같은 답**을 낸다. 재현성이
목적이므로 이게 핵심이다. 복도가 아니거나 방향성이 약하면 기존 격자 탐색으로
조용히 되돌아가며, 그때는 로그를 남긴다.

```
트랙내 점   3  680  216  431    0    1     ← 벽 반사가 "트랙 안 장애물" 로 분류됨
```

- 마스크가 **실제로는 벽인 181px 를 트랙 안쪽으로 포함** → 그 벽에 찍힌 라이다
  점이 장애물이 된다
- 반대로 진짜 주행 가능한 456px 는 누락

→ 마스크를 **맵의 자유공간에서 직접** 만든다. 거리변환으로 벽에서 `track_margin`
  (기본 0.20m) 이상 떨어진 곳만 "트랙 안" 으로 본다. 5cm 해상도라 실제 벽선을
  그대로 따라간다. 경계 폴리곤은 "트랙 밖 자유공간(피트 등)을 덜어내는" 용도로만
  선택적으로 겹친다(`use_bounds`, 기본 false) — 엉성해도 벽을 장애물로 만들지 않는다.

  ★ `track_margin` 은 라인 위 최소 여유(이 트랙 36cm)보다 작아야 한다. 크면
    좁은 구간에서 라인 자체가 마스크 밖으로 나간다.

**원인 2 — 점유 격자가 벽을 안쪽으로 두껍게 만든다.** `_scan_cb` 는
`|rho - range| < grid_safe_dist` 인 격자 셀을 점유로 본다. `grid_safe_dist: 0.3`
이면 벽면 기준 **안쪽으로 0.3m 두께의 띠**가 통째로 점유가 된다. 마스크 여유
0.20m 로는 그 띠를 못 걷어낸다.

→ `grid_safe_dist` 0.3 → **0.12** (격자 해상도 0.04m 의 3배, 충분한 여유).

**결과(같은 합성 스캔 재실행):** 6개 지점 전부 트랙내 점 **0** / 막힘 **0**.
벽만 있는 상황에서 회피가 아예 발동하지 않는다.

## 08/03 — IMU yaw 융합 구현·검증 + colcon prefix 그림자 사고

08/02 AMCL 발산의 1차 원인(가설 ①: odom 각속도가 서보 명령에서 나옴)에 대한 대응.
**벤치 검증까지 완료, 실주행 검증은 아직.**

### 1) IMU 실측 — 하드웨어부터 스케일까지 3단계

| 항목 | 결과 |
|------|------|
| IMU 존재 | ✅ VESC 6 MK6 HP, fw 6.6, `/sensors/imu/raw` **49.95 Hz** |
| 단위 | ⚠ 가속도 **g**, 자이로 **deg/s** — ROS 규격(m/s², rad/s) 아님 |
| 축 방향 | ⚠ 전방=IMU **-y**, 좌측=**+x**, 위=**+z** — 순수 z축 90° 회전 |
| yaw 부호 | ✅ 좌회전 = gyro **+z** (REP-103 일치) |
| 정지 바이어스 | 0.107 / 0.113 / 0.136 deg/s — **실행마다 다름** |
| 회전 스케일 | ✅ 3바퀴 1076.76° / 1080° = **0.9970 (-0.30%)** |

`vesc_driver` 는 원래부터 `requestImuData()` 로 IMU 를 폴링해 발행하고 있었다
(`/sensors/imu` VescImuStamped, `/sensors/imu/raw` sensor_msgs/Imu). 다만
`vesc_packet.cpp` 의 `acc_x() // g`, `gyr_x() // deg/s` 값을 **변환 없이 그대로**
`sensor_msgs/Imu` 에 넣는다(`vesc_driver.cpp:234~240`). REP-145 위반이라
그대로 `robot_localization` 에 물리면 yaw rate 가 57.3배 과소평가된다.

**축이 z축 90° 회전이라 운이 좋았다.** 회전축이 z 그대로라 yaw 는 축·부호 모두
손댈 필요가 없다. x/y 스왑은 가속도를 쓸 때만 문제가 된다.

**바이어스가 매번 달랐다는 게 설계 근거다.** 같은 날 세 번 측정에 0.107→0.113→0.136
deg/s. 상수로 박았으면 랩당 3° 가까이 틀렸다. MEMS 자이로 바이어스는 제조 공차·
납땜 응력·온도·전원에 따라 변하고, 특히 **turn-on bias 는 켤 때마다 다르다.**

### 2) `imu_odom.py` — 회전만 자이로로 교체

```
[vesc_to_odom] /odom ──┐
                        ├─► [imu_odom] ──► /odom_imu + TF odom→base_link
[vesc_driver] /sensors/imu/raw ─┘
```

- **yaw 만** 자이로로 다시 적분. 병진 속도는 휠 오도메트리(ERPM)가 정확하므로 유지
- 바이어스는 **정지할 때마다 측정**. 기동 후 3초 정지에서 확정, 이후에도 정지가
  감지되면 지수평균으로 갱신. 정지 판정은 `속도<0.05m/s` **AND** `자이로<2deg/s` —
  속도만 보면 제자리에서 밀릴 때 오염되고, 자이로만 보면 등속 직진을 정지로 오인한다
- **★ TF 발행 주체를 넘겨받았다.** AMCL·slam_toolbox 는 `/odom` 토픽이 아니라
  `odom→base_link` **TF** 를 본다. 그래서 `config/vesc.yaml` 의
  `vesc_to_odom_node.publish_tf` 를 false 로 끄고 이 노드가 발행한다.
  둘이 같은 transform 을 내면 TF 트리가 깨져 위치가 튄다.
  **이 노드가 없으면 odom TF 자체가 없다** — race/mapping launch 양쪽에 상주시켰고,
  `imu_yaw: false` 로 꺼도 노드는 뜬 채 들어온 odom 을 그대로 중계한다(롤백 안전)

### 3) 벤치 검증 결과 (`./race.sh box`, 바퀴 정지)

```
imu_odom 기동          ✅ 자이로 바이어스 확정: +0.1361 deg/s (152샘플)
vesc_to_odom → /tf     0 개   ← publish_tf: false 가 실제로 먹었다
imu_odom     → /tf     1 개   ← 발행자 단일
정지 20초 yaw 드리프트  0.234°
회전 스케일 (3바퀴)     -0.30%
```

오차의 **성질**이 바뀐 게 핵심이다. 서보 명령 기반 yaw 는 편향이라 시간에 비례해
커졌다(발산). 바이어스를 보정한 자이로에 남는 건 랜덤워크라 √t 로만 자란다.

### 6) 거리 캘리브레이션 준비 — yaw 다음 차례

yaw 는 해결했지만 **거리는 여전히 바퀴 회전수(ERPM)** 에서 나온다.
`speed_to_erpm_gain: 4614.0` 은 바퀴 둘레·기어비 가정값이라, 타이어 마모나 하중으로
유효 반경이 달라지면 **일정 비율로** 틀린다 (RC 타이어면 보통 2~5%).

오차 크기만 보면 yaw 보다 한참 작다 — 각도 오차는 주행 거리에 곱해져 지렛대가 붙기
때문이다.

```
yaw 13°/랩 → 30m 주행에서 횡방향 오차 ≈ 30 × sin(13°) = 6.7 m
거리 3%    → 30m 주행에서 종방향 오차 ≈ 0.9 m
```

**그런데 하필 AMCL 이 가장 못 잡아주는 성분이다.** LiDAR 스캔 매칭은 횡방향·각도는
잘 관측하지만 평행한 벽 사이에서 앞뒤로 미끄러지는 건 거의 관측하지 못한다
(aperture problem). 긴 직선에서 누적되다 코너에 가서야 교정된다. 그래서 우선순위는
낮아도 결국 잡아야 한다.

> ★ IMU 가속도 이중적분으로 거리를 얻으려 하지 말 것 — 바이어스가 t² 로 커진다.
> **EKF 를 붙여도 안 된다.** 속도 소스가 바퀴 하나뿐이면 스케일 오차는 어떤 필터로도
> 관측되지 않는다. 줄자나 맵 같은 절대 기준이 있어야만 잡힌다.

`odom_distance_check.py` 추가 — `∫|v|dt`(gain 이 직접 좌우) / 경로 길이 / 직선 변위
세 값을 동시에 재서 **직진 가정이 깨졌는지까지 판정**한다(뒤 둘이 2% 이상 벌어지면
경고). 뒤틀린 주행으로 게인을 고치면 yaw 오차를 거리 게인에 뒤집어씌우게 된다.
`--actual` 없이 측정만 해두고 나중에 실측값을 대입할 수도 있다(줄자 없을 때).

절차·판정기준은 `docs/odometry_calibration.md` 로 분리했다.

### 1) 증상 — 트랙이 커지자 AMCL 위치 오차가 누적돼 완전히 어긋남

지금까지 검증은 4.4×3.7m 소형 트랙에서만 했다. 오늘 처음 실제 규격 트랙을 깔고
주행하니 **주행이 진행될수록 추정 위치가 밀리다가 결국 맵과 스캔이 완전히 어긋났다.**

트랙이 커지면 두 가지가 동시에 나빠진다.
- 한 랩당 적분하는 거리·회전량이 커져 오도메트리 편향이 그만큼 크게 쌓인다.
- 벽까지 거리가 멀어져 스캔이 오도메트리를 붙잡아주지 못하는 구간이 길어진다
  (소형 트랙은 어디서든 벽이 코앞이라 편향이 있어도 매 스캔 즉시 교정됐다).

즉 **이전 트랙에서 안 보이던 게 아니라, 이전 트랙이 가려주고 있었다.**

### 2) 원인 가설 ① — odom 의 각속도가 "서보 명령"에서 나온다 (yaw 과대)

`config/vesc.yaml`:

```yaml
vesc_to_odom_node:
  ros__parameters:
    use_servo_cmd_to_calc_angular_velocity: true
    wheelbase: 0.33
```

odom 의 각속도는 측정값이 아니라 **서보 명령값을 조향각으로 역산해** 기구학 자전거
모델 `ω = v·tan(δ)/L` 로 계산한다. 그래서 아래 셋이 전부 yaw 과대 추정으로 들어간다.

- **서보 지연** — 명령은 목표값이고 실제 바퀴는 늦게 따라온다
  (`throttle_interpolator.max_servo_speed: 3.2 rad/s`, 시뮬에서는 `steer_delay: 14`
  = 140ms 로 모델링 중). 코너 진입마다 명령이 먼저 커져 실제보다 앞질러 적분한다.
- **타이어 슬립/언더스티어** — 기구학 모델은 슬립각 0 을 가정한다. 실제 yaw rate 는
  그보다 작고, 속도가 붙을수록 차이가 커진다.
- **조향 캘리브레이션 오차** — `steering_angle_to_servo_gain: -0.761` /
  `offset: 0.425` 가 틀어져 있으면 그 배율이 그대로 곱해진다.

주행 중 관찰한 "실제 조향보다 AMCL 이 더 많이 돈다고 생각한다" 는 이 경로와 정확히
일치한다. 게다가 `config/amcl.yaml` 은 `DifferentialMotionModel` + `alpha1/alpha2 = 0.2`
(회전 노이즈 작음) 라 이 편향을 파티클 분산으로 흡수할 여지가 좁고,
`recovery_alpha_slow/fast = 0` 이라 **한 번 어긋나면 전역 복구도 없다.**

### 3) 원인 가설 ② — IMU 미융합

현재 위치 추정 입력은 휠 오도메트리(ERPM) + 서보 명령 + 라이다 스캔뿐이고
자이로·가속도는 전혀 안 쓴다.

확인한 것: **드라이버 쪽은 이미 준비돼 있다.**
`vesc_driver.cpp` 가 타이머마다 `vesc_.requestImuData()` 를 호출하고
`sensors/imu`(`vesc_msgs/VescImuStamped`)·`sensors/imu/raw`(`sensor_msgs/Imu`) 로
발행한다 — 각속도·선가속도·쿼터니언 전부 담긴다.
남은 확인은 **이 보드에 IMU 가 실제로 붙어 있는지 하나뿐이다.**

### 4) 다음 세션 액션 (이 순서로)

### 5) 점검 필요 — 맵 이미지 스케일 vs 라이다가 보는 실제 지형

**아직 확인 안 한 전제:** RViz 에 뜨는 맵 이미지와 차가 라이다로 보는 지형의
**스케일이 실제로 일치하는지.** 여기가 틀어져 있으면 위 EKF/IMU 를 아무리 잘 해도

어디로도 못 가고, 증상은 "달릴수록 밀린다" 로 위 ①②와 **구분이 안 된다.**
그래서 EKF 작업보다 **먼저** 잘라내야 하는 항목이다.

확인 방법 (셋 다 5분):
1. **줄자 대조** — 맵 이미지에서 직선 벽 하나를 골라 픽셀 길이 × `resolution`(0.05)

2. **정지 상태 오버레이** — 차를 세워두고 RViz 에서 `/scan` 을 맵 위에 겹친다.
   스케일이 틀리면 **가까운 벽은 맞는데 먼 벽이 벌어지는** 패턴이 나온다
   (위치만 틀린 경우는 전체가 통째로 평행이동/회전한다 — 패턴이 다르다).
3. **SLAM 해상도 확인** — 맵 생성 당시 `slam_toolbox` 의 `resolution` 과
   `maps/sohot_clean.yaml` 의 `resolution: 0.05` 가 같은지. 다르면 여기서 갈린다.

### 6) gap_follower 로 완주 성공 — 대신 근거 없는 감속·정지 반복

**결과: 실물 트랙 완주 성공.** 오늘 실행 로그(`~/.ros/log`, 21:13 세션)에
`LAP 1 완료! (117.77s)` 가 남아 있다.

**왜 됐나:** `gap_follower.py` 는 `/scan` 과 `/race/enabled` 만 구독한다. **포즈를
전혀 안 쓴다.** 그래서 AMCL 이 어긋나든 말든 주행 자체는 영향을 안 받는다
("AMCL 을 안 써서 됐다" 는 관찰이 코드와 일치). 단 **랩 카운트는 여전히
`/amcl_pose` 기반**이라(`mission_manager`) 랩 수·자동정지는 못 믿는다.

**문제: 벽까지 거리가 넉넉한데도 충돌 위험으로 판단해 감속·정지를 반복.**
한 랩 117.77s 는 평균 0.3 m/s 대의 기어가기다.

먼저 **AEB 는 범인이 아니다.** `race_script.yaml` 의 `safety.enabled: false` 이고,
`race.launch.py` 는 이 값이 false 면 `safety_node` 를 **아예 띄우지 않는다**(147줄).
오늘 로그에도 safety_node 가 없다. `mission_manager` 의 `finish()` 도 일회성이라
"반복 정지" 를 만들 수 없다. 즉 **속도를 깎은 것은 gap_follower 자신이다.**

**유력 원인 — 속도 계산이 disparity 로 오염된 거리를 쓴다** (`gap_follower.py` 94~99):

```python
front_mask = np.abs(a) < np.deg2rad(10)
front_dist = float(np.mean(r[front_mask]))          # ← r 은 이미 확장된 배열
speed = np.clip(speed_gain * front_dist, min_speed, max_speed)
speed *= max(0.4, 1.0 - abs(steer) / max_steer * 0.6)
```

`r` 은 2단계 Disparity Extender 를 **거친 뒤** 값이다. 확장은 불연속 엣지 주변을
`car_width/2` 만큼 **더 가까운 값으로 덮어쓴다.** 확장 폭은
`n_ext = ceil(half_w / (closer·Δθ))` — `car_width 0.40` → `half_w 0.20`,
1m 거리의 엣지에 Hokuyo `Δθ ≈ 0.25°` 면 **약 45빔 ≈ ±11°.**
정면 판정 창이 ±10° 이므로 **옆쪽 모서리 하나가 정면 창을 통째로 덮어쓴다.**
정면은 훤히 뚫려 있는데 `front_dist` 가 옆 모서리 거리로 떨어지고, 그대로 감속된다.
이것이 "거리가 넉넉한데 충돌 위험이라 판단" 의 정체로 보인다.

여기에 두 가지가 겹친다.
- `speed_gain 0.5` — 정면이 3m 는 뚫려 있어야 겨우 `q2_max 1.5` 에 닿는다.
- 조향 감속 `max(0.4, ...)` — 조향이 포화되면 속도가 **60% 깎인다.**
  gap 이 좁게 잡히면 조향이 커지고 → 또 감속되는 되먹임.
- 결과 속도가 0.2~0.5 m/s 까지 내려가면 `speed_to_erpm_gain 4614` 기준
  **920~2300 ERPM** 이라 저 RPM 구간에서 모터가 툭툭 끊긴다 — 이게 "정지 반복" 으로
  보였을 가능성이 크다. 실제로 멈춘 게 아니라 못 굴러간 것.

**개선 방향 (다음 세션):**
1. **`front_dist` 를 확장 전 원본 거리에서 계산** — 확장은 "어디로 갈지"(조향)를
   고르기 위한 것이지 "얼마나 빨리 갈지" 의 근거가 아니다. 원본 `ranges` 의
   정면 ±10° 최솟값(평균보다 보수적이면서 오염은 없음)을 쓰는 쪽이 맞다. ★ 1순위
2. `gap_follower.car_width` 0.40 → 0.30~0.34 (확장 폭이 곧 안전 마진, 지금 과대)
3. `gap_follower.speed_gain` 0.5 → 0.8~1.0 (같은 정면 거리에서 더 내도록)
4. `speed.q2_max` 1.5 → 단계적 상향, `min_speed` 는 모터가 안 끊기는 하한으로
5. 조향 감속 계수 `0.6` / 하한 `0.4` 를 yaml 파라미터로 빼서 튜닝 가능하게
   (지금은 코드 상수라 `tune.sh` 로 못 만진다)

※ 값은 한 번에 하나씩 — `docs/next_real_test_checklist.md` 절차 준수.

## 07/21 — 튜닝 CLI + AEB 오발동 규명·재설계 + 벽 스침 회피

### 1) `tune.sh` — 게인 튜닝 CLI

주행 → RViz 관찰 → 게인 수정 → 재주행 루프를 에디터 없이 돌리기 위한 도구.
`race.launch.py` 가 매 실행마다 yaml 을 새로 읽으므로, 값만 바꾸면 다음 `./race.sh`
부터 반영된다 (**재빌드 불필요**).

**설계상 핵심:** `race_script.yaml` 은 주석이 곧 팀 문서다. `yaml.load → dump` 왕복은
주석·정렬·섹션 구분선을 전부 날린다. 그래서 **대상 한 줄만 정규식으로 치환**하고
`#` 이 있던 열까지 유지한다.

```bash
./tune.sh status              # 조절 우선순위 + 커밋 대비 변경분 + 최근 이력
./tune.sh stanley.gain=1.2    # 설정 (여러 개 동시 가능)
./tune.sh stanley.ff_gain+=0.3
./tune.sh --log / --diff / --undo
```

**안전 가드** (실차가 걸린 파일이므로): `ff_gain=0` 금지(yaml 주석의 "절대 0으로 두지
말 것"을 코드로 강제), 권장 범위 이탈, 한 번에 5배 이상 변경(`1.5`→`15` 오타), 타입
불일치. 쓰기 후 재파싱해 값이 의도대로 들어갔는지 검증하고 아니면 원본을 되돌린다.

`status` 의 조절 우선순위는 `docs/stanley_gain_tuning.md` 에서 가져왔다. `controller`
가 stanley 가 아니면 경고한다 — gap_follower 상태에서 Stanley 게인을 만져도 반영되지
않는 함정을 막는다. 문서: `docs/tune_사용법.md`

### 2) AEB 오발동 규명 — 원인은 "표준 공식" 그 자체

**증상:** `safety.enabled: true` 로 바꾸자 앞에 장애물이 없는데도 계속 제동.

**기존 판정식** (F1TENTH Lab2 표준 그대로였다):

```
iTTC = range / max(v·cos θ, ε)      전방 반평면 모든 빔 중 최솟값으로 판정
```

각도 제한이 `proj > 0.05` 하나뿐이라 **|θ| < 88.4° 전체**가 들어가고, `np.min` 이라
그 안의 빔 하나만 걸려도 발동했다. 라이다가 ±180° 전체를 보므로 사실상 전방 반평면 전부.

**구조적 결함:** 주행 방향과 나란한 벽은 차가 전진해도 그 빔의 range 가 거의 변하지
않는다(실제 range rate ≈ 0). 그런데 이 식은 접근 속도를 무조건 `v·cos θ` 로 가정하므로
**측면 기하에 대해 충돌을 체계적으로 과다 예측한다.**

> 참고: ForzaETH(F1TENTH 우승팀) 스택에는 이런 AEB 노드가 없다. perception 이
> **트랙 경계 기준으로 라이다 점을 걸러** 상대차만 뽑고 회피는 로컬 플래너가 한다.
> 이 저장소의 `stanley_controller` Q2 경로도 이미 `inner/outer_bound` 로 같은 일을
> 한다 — AEB 만 그 혜택을 못 받고 있었다.

### 3) AEB 재설계 — 주행 통로(swept corridor) 방식

```
1. 스캔 → 차량 좌표계 (x 전방, y 좌)
2. /odom yaw rate 로 R = v/ω → 주행 경로를 원호로 예측 (직진이면 직선)
3. 그 경로를 차폭만큼 부풀린 "통로" 안의 점만 남긴다  ← 나란한 벽은 여기서 제외
4. 호 길이 < v²/(2·brake_decel) + v·ttc_threshold  이면 제동
5. 연속 3프레임 검출 + min_range 0.12m 미만은 차체 반사로 폐기
```

`ttc_threshold` 는 이제 **반응시간** 의미이고 물리적 제동거리 `v²/2a` 가 더해진다
(v=1.8 → 정지거리 0.81m). 원호 예측 덕분에 코너에서 바깥 벽에 오발동하지 않는다.

**오프라인 검증 (합성 스캔, 실차 없이 19개 시나리오):**

| 시나리오 | 결과 |
|---|---|
| 나란한 벽 ±0.35~0.5m, 앞은 뚫림 | 통로 내 점 **0개** → 미발동 |
| 정면 수직 벽 0.5·0.7m (막다른 길) | **제동** |
| 45° 사선 벽 / 스핀으로 벽이 정면 | **제동** |
| 통로 밖 옆 장애물 (0.6, 0.6) | 미발동 |
| 차체 반사 0.08m | 필터됨 |
| 후진 중 뒤 장애물 / 앞 장애물 | 제동 / 미발동 |

즉 **벽을 무시하는 게 아니라, 옆을 스쳐 지나가는 것과 향해 가는 것을 구분**한다.

**한계 2건 (기록):**
- 나란한 벽만으로는 원래 오발동이 설명되지 않는다. 구식 방식도 벽 ±0.4m 에서
  min iTTC 0.444s 로 임계 0.15 보다 훨씬 크다. 실제 범인은 **근거리 반사(차체 등)**
  일 가능성이 높다 — `min_range` 와 연속 3프레임 조건이 그걸 노린다.
- 원호 통로는 "지금 조향을 유지한다" 가정이라 급코너에서 보수적이다. R=1.5m·벽 0.5m
  조합은 약 1.9 m/s 이상에서 발동한다.

**→ 실차에서 오발동이 잔존해 `safety.enabled: false` 로 두고 추후 개선하기로 함.**

### 4) 벽 스침 회피 (wall_avoid) — Stanley 보정 조향

"2시 방향에서 벽이 다가와 우측 전면이 스칠 것 같다" 는 상황용. AEB(정지)로는 못 막는
영역이다.

**판정은 "가장 가까운 점"이 아니라 침범량(encroachment):**

```
원하는 여유 = half_width(0.17) + clearance(0.18) = 0.35m
보정 = gain × (오른쪽 침범 − 왼쪽 침범),  ±0.10rad(5.7°) 로 제한
```

이 **뺄셈 구조**가 핵심이다. 나란한 벽은 여유 밖이면 침범 0 이라 보정이 안 나오고,
양쪽이 동시에 좁아지면 상쇄돼 가운데를 유지한다(그건 AEB 담당).

**Stanley 의 CTE 항이 이 보정에 저항하는 것이 안전장치다.** 보정을 넣으면 레이싱라인에서
밀려나 CTE 가 커지고 Stanley 가 되민다 → 유한한 횡변위에서 평형. 라인을 영구히 벗어나지
않는다. (코드 주석에 "일부러 없애지 말 것" 명시)

| 우측 여유 | 보정 조향 | 저항 후 실제 횡변위 |
|---|---|---|
| 0.35m↑ | 0° (불감대) | — |
| 0.30m | +1.7° | 3.7cm |
| 0.25m | +3.4° | 7.3cm |
| 0.20m | +5.2° | 11cm |
| 0.15m | +5.7° (포화) | 12cm |

**개발 중 잡은 설계 결함:** 처음엔 `w = 1 − x/lookahead` 로 "가까울수록 급하다"고
가중했는데 거꾸로였다. 수렴하는 벽은 위험 지점이 **앞쪽**인데 바로 거기를 0 으로 눌러,
벽이 y=−0.10(차 반폭 0.17 보다 안쪽 = 확실한 충돌)까지 와도 보정이 1° 밖에 안 나왔다.
감시창 1.2m 는 1.8m/s 에서 0.67초라 창 전체가 임박한 상황이므로, 가중 없이 **창 안 최소
여유**를 쓰도록 고쳤다 (1.07° → 5.73°).

**실차 결과: 1차 확인 OK.** 게인 추가 보정 필요.

### 5) CycloneDDS 전환 — 노트북 RViz 수신 안정화 (커밋 `d02cd9e`)

**증상:** 노트북에서 `ros2 topic list`로는 모든 토픽이 보이는데 RViz는 간헐적으로만 나오고
"map을 receive 못하고 있다"가 반복. 성공한 건 1번뿐.

**원인 추정:** `/map`(67KB)과 `/tf_static`은 `TRANSIENT_LOCAL`(래치)이라 늦게 접속한
구독자에게 과거 발행분을 다시 보내줘야 하는데, 기본 FastDDS + WiFi 조합에서 이 전달이
자주 실패한다. topic list는 discovery만 되면 뜨므로 정상으로 보인다.

**도입:** `config/cyclonedds.xml.in`(설정 템플릿), `config/dds_env.sh`(실행 시 자기 IP를
찾아 XML 생성 + 환경변수 export), `config/60-dds-buffers.conf`(커널 소켓 버퍼, 수동 설치),
`race_script.yaml`의 `network:` 섹션(팀원이 고치는 유일한 지점), `race.sh`/`rviz.sh` 자동 적용.

**핵심 튜닝 3가지**

1. **인터페이스를 IP로 고정** — 젯슨엔 주행망(192.168.45.x)과 LiDAR 전용망(192.168.0.x)이
   동시에 올라와 있다. 자동 선택에 맡기면 LiDAR 쪽을 잡아 노트북과 통신이 끊긴다.

### 7) 웨이포인트 곡률 스파이크 문제 수정

**증상:** 생성된 웨이포인트 일부 구간에서 곡률이 비정상적으로 뾰족함 (최대 κ=2.35).

**원인:**
- `snap_to_safe`가 벽 근처 점을 "가장 가까운 안전 픽셀"로 강제 이동 → 인접 점들은 그대로이므로 이동 전후 점 사이에 급격한 방향 변화(kink) 발생
- Step 4를 `arc_resample`(선형)으로 교체한 후 이 kink가 스무딩 없이 그대로 보존됨

**수정:** `smooth_constrained()` 함수 추가 — Laplacian 스무딩(이웃 평균 방향으로 alpha씩 이동) N회 적용 후 안전 검사 1회

```python
def smooth_constrained(x, y, dist_track, h, iters=5, alpha=0.3, min_m=None):
    xf, yf = x.copy(), y.copy()
    for _ in range(iters):
        xf = xf + alpha * (0.5 * (np.roll(xf, 1) + np.roll(xf, -1)) - xf)
        yf = yf + alpha * (0.5 * (np.roll(yf, 1) + np.roll(yf, -1)) - yf)
    return snap_to_safe(xf, yf, dist_track, h, min_m=min_m)
```

적용 위치: Step 3 최적화 종료 후, Step 4 리샘플링 종료 후 (각각 `snap_to_safe` 바로 뒤)

**결과:**

| 항목 | 수정 전 | 수정 후 |
|---|---|---|
| 최대 곡률 κ | 2.35 | 1.04 (-56%) |
| κ > 1.0 구간 수 | 15개 | 1개 |
| 최소 속도 | 1.94 m/s | 2.92 m/s |
| 예상 랩타임 | 17.7s | 15.7s |

- 8-연결 convolution 커널로 이웃 수 >= 3 픽셀 탐지
- 문제: 교차로 하나에 여러 픽셀이 뭉쳐서 검출됨 (픽셀 단위 특성)
- 해결: `ndimage.label`로 인접 픽셀 클러스터링 → 무게중심 1개로 대표

**(b) 90도 꺾임 오탐 문제**
- 대각선 구간에서 일반 경로 픽셀도 이웃이 3개로 카운팅됨
- 해결: 그래프 구축 후 **degree-2 노드 제거** (양옆 엣지를 합쳐서 1개로 병합, 반복)
- 결과: real_track4 기준 초기 8노드 9엣지 → 단순화 후 2노드 3엣지 (진짜 교차로만 남음)

**(c) 그래프 구축**
- 노드: 클러스터 무게중심 (float 좌표, 스켈레톤 위에 없어도 됨)
- 엣지 탐색: 클러스터 경계 픽셀에서 출발해 다음 클러스터까지 8-연결 픽셀 trace
- `pixel_cluster` 배열로 각 픽셀의 소속 클러스터를 O(1) 조회

### 8) `pure_pursuit_node.py` 웨이포인트 방향 자동 보정

**증상:** 로그에 `[PURSUIT]`가 찍히는데 레인을 따라가지 않고, 충돌 후 후진하면 오히려 제대로 따라감.

**원인:** 웨이포인트 배열 순서와 차량 초기 헤딩이 반대. `_find_lookahead`는 배열 인덱스 증가 방향으로만 탐색하므로, 방향이 반대이면 lookahead 목표가 항상 차량 뒤쪽에 잡힘. 후진으로 180° 돌아서야 우연히 방향이 맞아짐.

**수정:** `_find_lookahead` 첫 초기화 시 `dot(fwd_vec, wp_dir)` 부호 확인 → 음수이면 `self.wp = self.wp[::-1]` 자동 역전 + 경고 로그 출력.

```python
fwd = np.array([np.cos(yaw), np.sin(yaw)])
wp_dir = self.wp[(near + 1) % n, :2] - self.wp[near, :2]
if np.dot(fwd, wp_dir) < 0:
    self.wp = self.wp[::-1]
```

### 1) 비상 제동 시스템 개선 — 비례 제동 도입 및 후진 파라미터 강화

**문제:** 기존 충돌 회피는 전방 `COLLISION_THRESH(0.25m)` 이하가 돼야 후진을 시작했다. 감지 거리가 너무 짧아 벽에 거의 닿은 뒤에야 반응하는 문제가 있었다. 후진 속도(0.5m/s)·시간(2.0s)도 짧아 충분히 빠져나오지 못했다.

**수정 내용:**

**(a) 비례 제동 도입 (`BRAKE_START_DIST`)**
- 전방 장애물이 `BRAKE_START_DIST(2.0m)` 이내로 들어오면 거리에 비례해 속도를 줄이기 시작
- `COLLISION_THRESH`에 도달하면 속도 0으로 수렴 후 후진 전환

```python
if front_dist < self.BRAKE_START_DIST:
    brake_ratio = (front_dist - self.COLLISION_THRESH) / \
                  (self.BRAKE_START_DIST - self.COLLISION_THRESH)
    target_speed *= float(np.clip(brake_ratio, 0.0, 1.0))
```

**(b) 후진 파라미터 강화**

| 파라미터 | 변경 전 | 변경 후 |
|---|---|---|
| `REVERSE_SPEED` | 0.5 m/s | **0.8 m/s** |
| `REVERSE_DURATION` | 2.0 s | **3.5 s** |

**검증:** 벽 방향으로 스폰해 비례 제동 작동 및 후진 복구 확인.
