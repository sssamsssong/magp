# ★ map_optimize 의 grip_util 최적화 결과가 주행에 반영되지 않는다

**발견 2026-08-09 (젯슨). 코드는 안 고쳤다 — 어느 방식으로 맞출지 정해야 해서.**

## 증상

`map_optimize.py` 가 찾은 `grip_util` 이 실제 주행에 **전혀 적용되지 않는다.**
최적화는 정상적으로 끝나고 yaml 도 갱신되므로 **성공한 것처럼 보인다.**

```yaml
mode: q1

limits:
  grip_util:
    default: 0.743    # ← 옵티마이저가 여기 쓴다
    q1: 0.6           # ← launch 는 이걸 읽는다
    q2: 0.5
    q3: 0.75
    race: 0.6
```

젯슨에서 확인한 실제 해석 결과:

```
현재 mode: q1
★ launch 가 실제로 쓰는 값: 0.6
   옵티마이저가 쓴 값(default): 0.743
   → 무시됨 — mode 키가 default 를 가린다
```

## 원인

읽는 쪽과 쓰는 쪽이 서로 다른 키를 본다.

**읽기** — `race.launch.py:46-48` (그리고 `sim_race.launch.py:73` 도 동일)

```python
_gu = _lim.get('grip_util', 0.6)
grip_util = float(_gu.get(mode, _gu.get('default', 0.6))
                  if isinstance(_gu, dict) else _gu)
```

모드별 키를 **먼저** 본다. `q1` 이 존재하면 `default` 는 폴백이라 절대 안 쓰인다.

**쓰기** — `map_optimize.py:314-320`

```python
# limits.grip_util.default (4-space indent, unique key in this context)
if 'grip_util' in best:
    text = re.sub(r'^(    default:)\s+\S+', ...)
```

`default` 에만 쓴다.

그래서 `q1`~`race` 네 키가 전부 채워져 있는 현재 설정에서는 **`default` 가 어떤
값이어도 아무 모드에 영향을 주지 않는다.**

`map_optimize.py:356-358` 도 기준값을 `default` 에서 읽으므로, 옵티마이저는
**자기가 쓰고 자기가 읽는 값** 위에서 최적화한다. 주행이 쓰는 값(0.6)과 무관하다.

## 왜 이 구조가 됐나

두 작업이 엇갈렸다.

* 젯슨: 모드별로 위험도를 다르게 두려고 `grip_util` 을 dict 로 만들었다
  (q2 는 장애물 회피라 여유를 더 둔다 → 0.5).
* 노트북: 옵티마이저가 단일 값을 찾아 `default` 에 기록하도록 만들었다.

둘 다 각자 맞지만 합치면 `default` 가 죽는다.

## 어떻게 맞출까 (셋 중 하나)

### A. 옵티마이저가 **현재 모드 키**에 쓴다 — 권장

`mode: q1` 로 돌렸으면 `q1: 0.743` 에 기록한다. 기준값도 같은 키에서 읽는다.

* 모드별 위험도 구분이 유지된다 (q2 는 계속 보수적).
* 최적화한 모드에만 반영되므로 "어느 모드를 최적화했는지" 가 결과에 남는다.
* 옵티마이저의 정규식이 `default:` 대신 `{mode}:` 를 잡도록 바꾸면 된다.

### B. 모드별 키를 없애고 단일값으로

```yaml
limits:
  grip_util: 0.743
```

* 읽는 쪽 코드는 이미 단일값(스칼라)을 지원한다 — `isinstance(_gu, dict)` 분기.
* 가장 단순하지만 **q2 에서 회피 여유를 더 두는 설계가 사라진다.**
  장애물 구간에서 라인 주행과 같은 그립을 쓰게 된다.

### C. 옵티마이저가 모드별 키를 비율 유지하며 전부 갱신

현재 비율(q1 0.6 / q2 0.5 / q3 0.75 / race 0.6)을 유지한 채 스케일한다.
가장 "똑똑" 하지만 기준이 모호하고(무엇 대비 비율인가) 디버깅이 어렵다.

## 참고 — 반영되면 얼마나 달라지나

`halfhot_forza_opt_wp` (284점 28.2m), μ_eff 0.400 기준:

| η | 속도 범위 | 중앙 | 랩타임 |
|---|---|---|---|
| 0.600 (지금 실제) | 1.36~4.31㎧ | 2.57 | 12.0s |
| 0.743 (옵티마이저) | — | 약 +11% | 더 짧아짐 |

`v ∝ √η` 이므로 코너 속도가 약 11% 오른다.

## ⚠ 반영하기 전에

μ 는 아직 **추정치 0.400 ± 0.08** 이다 (실측 아님 — 2026-08-08 원 주행은 충돌
32%·휠 스핀으로 못 썼다). 옵티마이저의 0.743 은 **그 추정 μ 위의 시뮬 결과**라,
실차에서 그대로 쓰면 μ 오차와 η 상승이 겹친다.

실차는 `grip_util` 을 0.5 부터 0.1 씩 올리며 아래 신호로 한계를 찾는 편이 안전하다:

* 실측 a_lat(= v·ω, 롤 무관) 이 지령보다 낮은 곳에서 평평해짐 ← 그립 포화
* 횡추종오차가 초선형으로 증가
* 언더스티어비(ω_실측 / ω_기구학)가 벌어짐

그 한계 × 0.85 를 대회값으로 쓴다. 이 스윕이 곧 μ 재측정이기도 하다.

## 같은 종류의 함정 (이미 정리한 것)

읽는 곳과 쓰는 곳이 갈리면 "고쳤는데 아무 효과가 없으면서 고친 것처럼 보인다".
2026-08-09 에만 세 번 나왔다.

1. `grip_util`/`a_lon_*` 가 `[limits]` 와 `[map]` 양쪽에 있었다 → `[map]` 쪽 삭제
2. `map_controller` 가 프로파일을 만든 뒤 `max_speed` 로 다시 잘랐다 → 클램프 제거
3. **이 문서** — `default` vs 모드 키

새 파라미터를 넣을 때는 **읽는 곳이 한 군데인지** 먼저 확인할 것.
