# 다음 실차 세션 체크리스트 (2026-07-23 정리)

이전 세션(RViz 지연, 게인 튜닝, 속도 조정)에서 겪은 사고 2건(ff_preview_sec
0.38→0.7 공진, q2_max 1.5→3.0 급점프 충돌)을 근거로 정리한 절차. 즉흥적으로
값을 바꾸지 말고 아래 순서대로.

## 시작 전

- [ ] `bat.sh`로 배터리 확인
- [ ] `./tune.sh status`로 지금 게인·속도 상태가 마지막 커밋 대비 뭐가
      바뀌어 있는지 확인 (모르고 이전 실험값 그대로 켜는 것 방지)
- [ ] `ros2 lifecycle get /map_server`, `/amcl` 이 `active`인지 확인
      (아니면 RViz 지연/파란 경로 미출현 문제 재발)

## 값 하나 바꿀 때마다

- [ ] **한 번에 하나만** 바꾼다 (게인이든 속도든)
- [ ] 속도는 `q2_max`가 아니라 **`vel_scale`로 비례 축소** — 코너/직선 속도
      차이를 유지한 채 저속 테스트 (예: `vel_scale=0.625` → 최고속 2.5로)
      단, `q2_max`도 그 이상으로 같이 올려둘 것 (안 그러면 다시 클립됨)
- [ ] 증분은 작게: 속도 ±0.3~0.5 m/s, 게인도 소폭씩
- [ ] **CSV 속도 바닥 2.523 m/s 부근을 지날 때는 특히 신중히** — 이 지점부터
      처음으로 코너별 실제 속도 차이가 살아남

## 저속에서 다음을 확인 후에만 속도를 더 올린다

- [ ] RViz에서 파란 실주행 경로가 코너에서 매끈하게 바깥으로 밀리기만 하는지
      (오실레이션 없음) — 이건 언더스티어, 게인으로 대응
- [ ] 아니면 좌우로 흔들리는지(오실레이션) — 이건 게인/타이밍 문제,
      즉시 롤백 (`./tune.sh --undo`)
- [ ] `/drive`의 `steering_angle`이 코너에서 `max_steer(0.36)`에 포화되는지
      ```bash
      ros2 topic echo /drive --field drive.steering_angle
      ```
      포화돼 있으면 게인 더 올려도 무의미 — 그 구간 목표속도를 낮춰야 함

## 기록

- [ ] Notion "Stanley 조향 게인 값 실험실"에 게인 6종 + **그 시점의 max_speed
      (q2_max 또는 vel_scale)** 도 같이 기록 — 게인의 좋고 나쁨은 이제
      속도에 종속적이라 속도 없이는 기록 의미 없음
- [ ] 좋은 값을 찾으면 커밋 (`tune.sh`는 파일만 고치고 커밋은 안 함)

## AEB / wall_avoid 재검증 시 (지금은 둘 다 `enabled: false`)

- [ ] **`safety_node.py`에 라이다 오프셋(`laser_offset_x=0.27`) 보정이
      빠져 있음 — 코드 리뷰에서 발견, 아직 미수정.** `stanley_controller.py`의
      Q2 장애물 판정은 이 오프셋을 명시적으로 빼고 계산하는데(822~828줄,
      "장애물 점 1개" 버그의 원인이었던 바로 그 보정), `safety_node.py`의
      `_closest_in_corridor`는 스캔 (x,y)를 원점 보정 없이 그대로 써서 통로
      중심(회전축, base_link 원점 가정)과 0.27m 어긋난 상태로 판정한다.
      통로 반폭이 0.30m이라 이 정도 오차는 판정을 충분히 뒤집을 수 있는
      크기 — **AEB 오발동 잔존의 유력한 원인 후보.** 재활성화 전에 이 보정을
      먼저 넣고 재검증할 것.
- [ ] 저속에서부터 켜고, 오발동 시 `/aeb_corridor` 마커로 어떤 점이 범인인지
      RViz에서 확인

## 시뮬(`sim.sh`) 활용

- [ ] 실차로 못 하는 속도 스윕은 먼저 시뮬에서 (`vel_scale`/`q2_max` 동일하게
      조정 가능)
- [ ] `sim_vehicle`(mu, C_Sf, sv_max, steer_delay) 캘리브레이션은 현재
      저속(1.5m/s대 균일주행) 데이터로만 맞춰진 것 — 새로 테스트하는 속도
      구간에서 실차-시뮬 패턴이 어긋나면 그 속도대에서 mu/C_Sf 재조정
      (밀리면 mu↓/sv_max↓/steer_delay↑, 파고들면 반대)
- [ ] 웨이포인트 속도 프로파일을 더 보수적인 마찰계수로 재생성해볼 후보값
      (x,y는 기존과 동일, 속도열만 재계산):

      | mu | 최저속도(m/s) | 랩타임 추정(s) |
      |---|---|---|
      | 0.9 (현재) | 2.52 | 3.79 |
      | 0.7 | 2.24 | 4.03 |
      | 0.6 | 2.07 | 4.20 |
      | 0.5 | 1.89 | 4.44 |
      | 0.4 | 1.69 | 4.81 |

      mu=0.5까지 낮춰도 최저속도가 1.89로, 지금 자주 테스트하던 1.5보다
      여전히 높다 — 실차가 1.5 근방에서도 이미 밀린다면 실제 그립이 0.5보다
      낮을 가능성. `gen_waypoints.py --map track_2nd_clean --mu <값>`으로
      재생성 가능(단, 스켈레톤 후보 준비 후 대화형 GUI로 라인을 다시
      그려야 해서 완전 자동화는 안 됨 — 좌표는 그대로 두고 속도만 다시
      계산하려면 `speed_profile()` 함수만 재사용하는 스크립트 필요).
