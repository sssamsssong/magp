## 2026-08-11 — μ 0.42 확정 · 출발 슬립 해결 · q1 안정화

### 요약

**q1 이 마찰 예산 100%(η=1.0)로 안정 주행한다.** `fun_clean` 3랩 완주,
베스트 랩 **14.00s**(최고 5.05㎧). 어제까지 15.4~17.5s 였다.

### μ = 0.42 로 확정

한계를 **위아래로 짚었다**:

| μ | η | 결과 |
|---|---|---|
| 0.40 | 0.6~0.7 | 여유 있음 (제동 예산의 45%만 사용) |
| **0.42** | **1.0** | **깨끗하게 완주** |
| 0.45 | 1.0 | 코너 슬립 — 벽에 닿을 뻔 |

추정값이 아니라 양쪽에서 좁혀진 값이다. `μ_eff = 0.42 × 1.15 = 0.483`.

로그상 곡률비(주행 곡률 ÷ 기준)가 가장 빠른 주행에서 0.84 로 낮았다
= 바깥으로 밀렸다는 뜻이고, 보고된 슬립과 방향이 일치한다. 0.91 이 지금 자리.

> ⚠ 대회 노면(우레탄)에서는 다시 잴 것. **η 스윕이 곧 μ 측정이다.**

### 출발 급가속 슬립 — 해결 (`LaunchLimiter`)

**가설(팀):** "출발 위치가 직선 한가운데라 출발하자마자 급가속을 한다.
그래서 늘 첫 랩 첫 코너를 못 잡은 것 아니냐."

**맞았다.** 다만 확인하는 과정에서 **틀린 측정을 두 번 버렸다**:

1. **CTE 로 비교 → 차이 없음.** 당연하다. CTE 는 횡방향이고 문제는
   종방향이다. 위치가 앞서 나가도 CTE 는 깨끗하다.
2. **`amcl − odom` 을 차체좌표로 분해 → 부호가 반대로 나옴.** 두 프레임
   사이에 회전이 있으면 원점에서 멀수록 차이가 커져서, 그 미분이 회전
   성분에 오염된다.

**프레임에 무관한 측정:** 0.6초 창에서
`odom 이 말하는 이동거리 ÷ AMCL 이 말하는 이동거리`. 둘 다 스칼라
경로길이라 프레임 오프셋·회전과 무관하다. 1보다 크면 헛돈 것.

bag 16개:

```
가속도[㎧²]    출발 0~5s   5s 이후    차이
0.0~0.8         1.0332     1.0246    +0.86%
0.8~1.6         1.0344     1.0268    +0.76%
1.6 이상        1.0694     1.0360    +3.34%   ← 두 배
```

**같은 가속도인데도 출발 5초 안쪽이 더 미끄러진다.** 단순히 "가속하면
미끄러진다" 가 아니라 출발 자체가 특별하다 — 정지마찰 깨기, 구동계 백래시,
하중이 뒤로 쏠리며 앞이 뜨는 것이 겹친다.

누적 결과 **출발 5초에 허위거리 87cm**. 종방향은 복도에서 거의 관측되지
않으므로(앞뒤 0.2~1.0cm vs 좌우 6~7cm) AMCL 이 다 못 되돌리고 자세에 남는다
→ "실제보다 더 갔다" → **첫 코너 조기 진입.**

**대책:** `speed_profile.LaunchLimiter` (map·stanley 공용).
`launch_acc`(0.8㎧²) 로 시작해 `launch_time`(3s)에 걸쳐 `a_lon_acc`(1.6)로
**선형 복귀**. 감속에는 안 건다.

- 계단으로 풀지 않는 이유: 그 순간 지령이 튀는데(차가 프로파일보다 뒤처져
  있으니까) 그 계단이 곧 풀스로틀이라 막 벗어난 스핀 조건으로 도로 들어간다
- 창이 끝나도 `a_lon_acc` 로는 계속 건다. 프로파일이 이미 **공간상** 지키는
  값이라 정상 주행에서는 안 걸린다

**검증 (같은 지표, 전/후 bag):**

```
출발 5초 누적 허위거리    87.3cm  →  17.6cm     (−80%)
단위거리당               5.29cm/m →  1.11cm/m   (−79%)
같은 5초에 간 거리       17.35m  →  15.89m     (−8%)
```

거리는 8%만 줄었는데 허위거리는 80% 줄었다 — **"천천히 가서 덜 쌓인" 게
아니라 실제로 덜 미끄러진 것**이다.

**비용:** 1랩 +1.16s. 누적되지 않는다(3랩 +1.20s). 창 길이는 거의 무의미하다
(1.5s 든 3.0s 든 0.1s 차이) — 실제 노브는 `launch_acc` 하나다:
`0.6→+1.30s / 0.8→+1.16s / 1.0→+1.02s / 1.2→+0.90s`.

### `gains.yaml` 이 조용히 거짓말하고 있었다

차량별 값 분리(`.car`) 이후 **mu·grip_util·l1_k 같은 실제로 주행을 결정한
값이 `race_script.yaml` 에 없다.** 그런데 주행 스냅샷은 그 파일만 복사했다.

→ 08/10~11 로그를 사후 분석할 때 "이 주행의 mu 가 얼마였나" 를 읽을 수
없었다. `gains.yaml` 에는 덮이기 **전** 값(0.348)이 찍혀 있고 실제로는
0.42 로 돌았다. **없느니만 못하다.**

`write_run_config()` 로 통일(세 컨트롤러 공용). 차량 오버레이를 구분선
아래에 덧붙여, 나중 키가 이기는 순서 = 실제 적용 순서로 남긴다.
오버레이가 없으면 그 사실을 파일에 경고로 적는다.

### `race_script.yaml` 이 깨져 있었다

`safety.hold_sec` 주석이 중간에 접혀 "재개" 가 다음 줄로 넘어가 있었다.
YAML 파서가 죽어 **다음 주행이 기동조차 못 했을 것이다.** 되붙였다.

## 2026-08-10 (밤) — 휠 스핀 규명 · alpha3 되돌림

### AMCL 이 계속 차를 뒤로 당기고 있었다

AMCL 보정의 종방향 성분을 가속도별로 재니 **전부 음수이고 가속에 비례**했다
(횡방향은 부호도 크기도 일정치 않음) → 종방향에만 있는 **계통 오차**.
잡음이 아니다. 08/08 슬립 분석의 "휠이 1.21배 빨리 돈다" 와 같은 현상인데,
그때는 μ 측정 오염 요인으로만 봤고 **위치추정에도 들어가고 있었다.**

### `alpha3` 0.03 → 0.12 (직전 판단 되돌림)

종방향에 두 요인이 맞선다:

- **(가)** 진행방향은 관측되지 않는다 → odom 을 믿어야 한다
- **(나)** 그런데 그 odom 이 가속 중에 계통적으로 틀린다

**(나)가 이긴다.** odom 이 계통적으로 틀리는데 `alpha3` 를 조이면 틀린 값을
더 믿게 만든다. 직전 커밋은 **(가)만 보고** 내린 결정이었다 — 관측 기하만
보고 센서 편향을 안 봤다.

### `a_lon_acc` 0(자동) → 1.6㎧²

자동 유도는 `μ_eff·g·lf/L = 2.48㎧²` 인데 실측 급가속은 **1.61㎧²**.
**낼 수 없는 가속을 1.5배로 요구하고 있었고, 그 차이가 휠 스핀으로 나갔다.**
랩타임 손해는 거의 없다 (η0.6: 15.7 → 15.6s) — 코너가 촘촘해 긴 가속 구간이
없어서다.

## 2026-08-10 (낮) — 차량별 설정 분리 · 라인 생성기 재작성

### 코드는 합치고 값만 분리 (`.car`)

브랜치로 차를 나누면 **코드까지 갈라져 같은 버그를 두 번** 고치게 된다.
실제로 그랬다 — bench(box) 수정을 두 차가 각자 디버깅해 각자 커밋했다.

```
config/vesc_base.yaml       배관. 두 차 공용, git
config/vehicle_car1.yaml    1호차 실측값,      git
config/vehicle_car2.yaml    2호차,             git
.car                        "car2" 한 줄       .gitignore
        ↓ config/apply_vehicle.py  (race.sh 가 매 실행 호출)
config/vesc.yaml                생성물  .gitignore
config/.vehicle_overlay.yaml    race_script.yaml 위에 덮을 값  .gitignore
```

`config/vesc.yaml` 이 git 에서 빠졌다 — **차량 캘리브레이션을 잘못 커밋할
방법 자체가 없어졌다.**

`max_steer` 는 손으로 적지 않는다. `(servo_min − offset) / (−gain)` 으로
`apply_vehicle.py` 가 계산한다. 08-09 에 `steer_trim` 이 offset 을 옮겼는데
`max_steer` 가 그대로여서 **좌 조향 지령의 25.8% 가 조용히 잘려 나갔다.**

### `ROS_DOMAIN_ID` 분리 (1호차 57 / 2호차 77)

도메인이 다르면 멀티캐스트 그룹과 포트 대역 자체가 달라 `/scan`·`/map`·`/tf`
가 절대 안 섞인다. 노트북은 `./rviz.sh 77` 로 붙을 차를 고른다.

> ⚠ 젯슨과 노트북이 **양쪽 다** `git pull` 해야 서로 보인다.

### `gen_raceline` 재작성 — `--rmin` 이 안 먹던 이유

세 겹이었다:

1. 내가 쓴 수렴식이 제약을 **느슨하게** 하는 방향이었다 (`r_eff *= r_act/rmin`)
2. **최적화한 곡선과 출력 곡선이 달랐다** — QP 는 `calc_splines` 로 풀고
   출력은 `splprep` 로 다시 매끈하게 만들고 있었다
3. 선형화가 무효해질 만큼 크게 움직였다 → 재선형화 반복(iqp) + 신뢰영역

중심선이 벽에 붙던 것도 고쳤다 (재중심화 12회). 부호를 처음에 반대로 넣어
비대칭이 70%→97% 로 **악화**했고, 양쪽을 실측해 `+n` 이 맞음을 확인했다
(70%→10%).

### bench(box) 모드가 무력화돼 있었다 — 실차 사고

`./race.sh box` 가 **시작 버튼도 없이 풀속도 자율주행**을 했다. 원인 두 겹:

- bench 가 "컨트롤러의 `clip(v, min, max)` 에 기대는" 구현이었는데,
  속도 개편에서 **그 클램프를 없앴다**
- `start_gate` 도 `and not bench` 로 함께 꺼져 있었다

→ 이제 각 컨트롤러의 **발행 직전** 한 곳에서 속도를 0 으로 못박는다.
**안전 기능을 다른 코드가 우연히 하는 일에 얹으면 안 된다.**

## 2026-08-09 — q2 속도 버그 · 요 진동 · η 스윕

### `./race.sh q2` 가 q1 의 속도로 달리고 있었다

`grip_util` 을 `mode:=` 오버라이드 **전에** 풀고 있었다. 컨트롤러는 q2(회피)로
뜨는데 속도는 q1(η=0.8) 이라 **4.9㎧ 로 장애물에 돌진**했고, 회피가 "전혀 안
되는" 것처럼 보였다. q2 주행의 `cmd_v` 중앙이 q1 과 동일한 3.02㎧ 로 찍혀
드러났다.

**즉, 회피 로직 자체는 아직 제대로 시험된 적이 없다.**

### 고속 직선 요 진동

- `steer_alpha` — 이 값이 **루프 주기에 걸려 있다.** 실차 50Hz 에서 170ms,
  시뮬 250Hz 에서 34ms. 같은 숫자가 5배 무겁다. 옵티마이저 결과를 그대로
  옮기면 안 되고 **시정수로 환산**해야 한다
- `l1_k` 0.5837 → 0.75 — α_f 가 `a_lat ∝ v` 라 L1 의 속도무관 설계를 깬다

### `slip_gain` 0.5 — 코너에서 안쪽으로 파고들던 것

주행 곡률이 기준의 1.2~1.9배였다. 슬립보정이 기구학항만큼 커진 상태.
0.5 로 낮춰 1.00~1.07 로 정상화.

### `speed_lag` 0.40 — 코너 진입 과속

지령↔실측 상호상관 실측 406~440ms. 속도가 오르니 지연도 늘었다
(저속에선 250~290ms). 제동 자체는 문제없고 **늦게 시작하는 게** 문제였다.

### AMCL 슬루 제한

보정을 즉시 전부 반영하고 있었다 — 4.5m 점프가 그대로 풀조향으로 나갔다.
정상 보정 p99 3.63㎧ vs 점프 254㎧ 를 재고 4.0㎧ 로 잘랐다(0.8% 만 잘림).

### η 스윕 = μ 측정

`cool_clean` 에서 η=1.0 으로 2.95랩 완주 → **μ_eff ≥ 0.400 확정**
(그 전까지는 추정 0.40±0.08).
