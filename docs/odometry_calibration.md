# 오도메트리 캘리브레이션 — 회전(yaw)과 거리

위치추정이 어긋나면 컨트롤러 게인을 아무리 만져도 소용없다. 추종 오차처럼 보이지만
원인은 "내가 어디 있는지 모른다"이기 때문이다. 이 문서는 그 아래 단계 —
**odom 이 말하는 회전과 거리를 실측에 맞추는 절차**를 다룬다.

---

## 0. 먼저 — odom 이 뭐고 왜 중요한가

`odom` 은 자기 센서만으로 "출발한 자리에서 얼마나, 어디로 갔는지"를 누적한 추정이다.
이 차에서는 두 값으로 만든다.

```
얼마나 갔나 ← 바퀴 회전수 (VESC ERPM)
어디를 보나 ← yaw  (2026-08-03 부터 IMU 자이로, 그 전엔 서보 명령)
```

**AMCL 은 odom 을 버리는 게 아니라 "예측값"으로 쓴다.** 파티클을 odom 이 말하는 만큼
움직여 놓고, LiDAR 스캔으로 그중 맞는 놈을 고른다. 그래서:

- odom 오차가 **랜덤**이면 → 파티클이 퍼지고 스캔이 골라준다 → 수렴한다
- odom 오차가 **편향**이면 → 파티클 전체가 같은 방향으로 끌려간다 → 스캔이 되돌리는
  것보다 끌려가는 게 빠르면 **놓친다**

2026-08-02 실물 트랙에서 AMCL 이 발산한 게 정확히 후자였다. 그러니 캘리브레이션의
목표는 "오차를 0으로" 가 아니라 **"편향을 없애서 랜덤만 남기는 것"** 이다.

프레임 관계는 REP-105 그대로다.

```
map ──(AMCL)──> odom ──(imu_odom)──> base_link
 절대 위치       누적 오차 흡수용      추측항법
```

## 1. 회전(yaw) — 2026-08-03 완료

### 무엇이 문제였나

`config/vesc.yaml` 의 `use_servo_cmd_to_calc_angular_velocity: true` 때문에
각속도를 **서보 명령값**으로 계산했다 (`ω = v·tan(δ)/L`).

- 명령은 목표값이라 실제 바퀴보다 앞선다 (서보 지연)
- 기구학 자전거 모델은 타이어 슬립각을 0 으로 가정한다

둘 다 yaw 를 **과대** 적분하는 방향이라, 편향이 시간에 비례해 쌓였다.

### 무엇으로 바꿨나

`imu_odom` 노드가 VESC 자이로의 yaw rate 로 다시 적분한다. 병진 속도는 휠
오도메트리 그대로. `race_script.yaml` 의 `localization.imu_yaw: false` 로 롤백 가능
(그 경우 들어온 odom 을 그대로 중계한다).

### 검증 도구

```bash
python3 ~/yax/imu_axis_check.py          # 축·부호 (드라이버만 있으면 됨)
python3 ~/yax/imu_yaw_scale_check.py --turns 3   # 스케일 (스택 필요)
```

`imu_axis_check.py` 는 정지 / 앞들기 / 좌회전 / 우로기울이기 4단계를 안내하고,
물리 방향 → IMU 축 대응표와 REP-103 일치 여부를 출력한다.

### 2026-08-03 실측 결과

| 항목 | 결과 |
|------|------|
| 축 | 전방 = IMU **-y**, 좌측 = **+x**, 위 = **+z** (순수 z축 90° 회전) |
| yaw 부호 | 좌회전 = gyro **+z** — REP-103 일치, 손댈 것 없음 |
| 회전 스케일 | 3바퀴 1076.76° / 1080° = **0.9970 (-0.30%)** ✅ |
| 정지 바이어스 | 0.107 / 0.113 / 0.136 deg/s — **실행마다 다름** |

**바이어스를 상수로 박으면 안 된다.** 같은 날 세 번 측정에 저만큼 달랐다. MEMS
자이로 바이어스는 제조 공차·납땜 응력·온도·전원 전압에 따라 변하고, 특히 켤 때마다
다르다(turn-on bias). 그래서 `imu_odom` 은 **정지할 때마다 직접 잰다** —
기동 후 3초 정지에서 확정하고, 이후에도 정지가 감지되면 지수평균으로 갱신한다.

> 출발 전 몇 초는 차를 세워둘 것. 안 그러면 바이어스 미보정 상태로 달리고,
> 노드가 경고를 띄운다.

## 2. 거리 — 미완

### 무엇이 문제인가

거리는 여전히 바퀴 회전수에서 나온다. `config/vesc.yaml`:

```
speed = (erpm - speed_to_erpm_offset) / speed_to_erpm_gain
                                        └─ 현재 4614.0
```

이 gain 은 바퀴 둘레·기어비·극수 가정에서 나온 값이다. 오차 출처는 셋:

1. **스케일 오차** — 타이어가 닳거나 하중으로 눌리면 유효 반경이 달라진다.
   RC 타이어면 보통 2~5%. **일정 비율로 틀리므로 편향이다** (거리에 비례해 누적)
2. **슬립** — 가속할 때 바퀴가 지면보다 빨리 돈다. 항상 과대추정 방향이라
   랩을 돌아도 상쇄되지 않는다
3. **저속 부정확** — 낮은 ERPM 에서 추정이 나빠진다. 0.2~0.5 m/s 는
   920~2300 ERPM 이라 이 구간에 들어간다

### 왜 yaw 보다 우선순위가 낮았나

각도 오차는 **주행 거리에 곱해져서** 위치 오차가 된다. 지렛대가 붙는다.

```
yaw 13°/랩  → 30m 주행에서 횡방향 오차 ≈ 30 × sin(13°) = 6.7 m
거리 3%     → 30m 주행에서 종방향 오차 ≈ 0.9 m
```

### 그런데 AMCL 이 제일 못 잡아주는 게 이것이다

LiDAR 스캔 매칭은 횡방향과 각도는 잘 관측하지만, **평행한 벽 사이에서 앞뒤로
미끄러지는 것은 거의 관측하지 못한다** (aperture problem). 1m 앞이나 뒤나 스캔
모양이 같기 때문이다. 긴 직선에서 계속 누적되다가 코너에 가서야 교정된다.

그래서 우선순위는 낮아도 **결국 잡아야 하는 항목**이다.

### ★ IMU 가속도로 거리를 얻으려 하지 말 것

두 번 적분하면 바이어스가 t² 로 커진다. 자이로 바이어스와는 비교가 안 되게 빨리
발산해서, 지상 로봇에서는 하지 않는다.

**EKF(robot_localization)를 붙여도 해결되지 않는다.** 속도 소스가 바퀴 하나뿐이면
스케일 오차는 어떤 필터로도 못 없앤다 — 줄자나 맵 같은 **절대 기준**이 있어야만
잡힌다. 이건 필터링 문제가 아니라 관측 문제다.

## 3. 거리 캘리브레이션 절차

### 준비물

- 줄자 (또는 길이를 아는 직선 구간 — 복도 타일 개수도 된다)
- 직선 10m 이상 확보. **길수록 정확하다** — 출발/도착 표시 오차가 그만큼 희석된다

### 순서

**1) 스택 기동** — 수동 주행이 가능한 모드로

```bash
cd ~/yax && ./race.sh joy          # 조이스틱 수동
# 또는 ./race.sh mapping-joy
```

**2) 측정** — 다른 터미널에서

```bash
python3 ~/yax/odom_distance_check.py              # 측정만 (줄자 없을 때)
python3 ~/yax/odom_distance_check.py --actual 10.0   # 실측값 있으면 게인까지
```

Enter → 조이스틱으로 직진 → 도착선에서 완전히 멈추고 Enter.

**주행 요령** (오차를 줄이는 순서대로)

- **등속 중속**으로. 급가속은 바퀴가 헛돌아 거리를 과대추정한다
- 되도록 직진. 코너를 돌면 안쪽/바깥 바퀴 차이가 섞인다
- 2~3회 반복. 매번 크게 다르면 슬립이 심한 것이다

**3) 결과 읽기**

스크립트는 세 값을 같이 낸다. 셋을 비교하면 뭐가 문제인지 드러난다.

| 값 | 의미 |
|----|------|
| `∫|v|dt` | ERPM 적분. **gain 이 직접 좌우하는 값** — 보정은 이걸 기준으로 |
| 경로 길이 | pose 누적. yaw 가 섞인다 |
| 직선 변위 | 시작→끝 직선거리. 정말 직진했다면 위 둘과 같아야 한다 |

경로 길이와 직선 변위가 2% 이상 다르면 직진이 아니었던 것이다 — 다시 잰다.

**4) 적용**

```
new_gain = 4614.0 × (오도메트리 거리 / 실제 거리)
```

`speed = erpm / gain` 이므로, 오도메트리가 과대추정(비율 > 1)이면 **gain 을 키운다.**

`config/vesc.yaml` 의 `speed_to_erpm_gain` 을 새 값으로 바꾼다.

> ⚠ `config/vesc.yaml` 은 repo 가 원본이고 `~/f1tenth_ws` 로 심링크돼 있다.
> **f1tenth_stack 을 colcon build 하면 install 링크가 복사본으로 덮인다.**
> 그 경우 `./install_on_jetson.sh` 로 재링크해야 값이 실제로 먹는다.

**5) 검증**

같은 구간을 다시 재서 오차가 1% 안으로 들어오는지 본다.

### 판정 기준

| 오차 | 해석 |
|------|------|
| < 1% | 보정 불필요 |
| 1~5% | 전형적인 타이어 반경 오차. 보정하면 좋다. 2~3회 재서 **같은 방향으로** 치우치는지 먼저 확인 |
| > 5% | 슬립이 심했거나 gain 이 많이 틀어졌다. 더 낮은 속도로 다시 잴 것 |

한 번의 측정으로 판단하지 말 것. **편향과 산포를 구분해야 한다** — 매번 같은 방향으로
치우치면 스케일 오차(보정 대상), 방향이 들쭉날쭉하면 슬립(보정으로 못 고침)이다.

## 4. 전체가 잘 맞는지 보는 법 — `map→odom`

캘리브레이션이 끝났으면 실주행에서 이걸 본다.

```bash
ros2 run tf2_ros tf2_echo map odom
```

이 변환이 곧 **"AMCL 이 odom 의 거짓말을 얼마나 되돌려야 했나"** 다.

| 관찰 | 해석 |
|------|------|
| 거의 고정 | odom 이 정확하다 ✅ |
| 랩이 돌수록 계속 커짐 | odom 이 여전히 샌다 — 어느 성분인지 위 절차로 분리 |
| 툭툭 점프 | AMCL 이 뒤늦게 크게 보정 중 — 위험 신호 |

RViz 에서 **스캔이 맵 벽에 붙어 있는지**가 최종 판정이다. 한 랩 내내 붙어 있으면 성공.

## 5. 순서 — 이 순서를 지킬 것

1. **맵 스케일 검증** (미완) — 맵 이미지와 실제 지형의 축척이 맞는가.
   여기가 틀어져 있으면 아래를 다 해도 AMCL 은 수렴하지 않고, 증상도 구분이 안 된다.
   정지 상태에서 `/scan` 을 맵에 겹쳐 **가까운 벽은 맞는데 먼 벽만 벌어지면** 스케일 문제,
   전체가 통째로 밀려 있으면 위치 문제다
2. **yaw** (완료) — 편향이 가장 크고 지렛대가 붙는다
3. **거리** (미완) — AMCL 이 못 잡아주는 성분이라 결국 필요하다
4. 그다음에 컨트롤러 게인 ([stanley_gain_tuning.md](stanley_gain_tuning.md))

**위치가 틀린 상태의 추종 오차는 게인 문제가 아니다.** 순서를 건너뛰면 엉뚱한 값을
튜닝하게 된다.
